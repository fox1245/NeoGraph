# JARVIS オーケストレーション ベンチマーク — NeoGraph と LangGraph

**Languages:** [English](README.md) | [한국어](README.ko.md) | [日本語](README.ja.md) | [简体中文](README.zh-CN.md)

同一のトポロジをミラーリング (マイク→stt→マージ→メモリ→ルーター→4-way→シンセ/スキップ→コミット→tts)
NeoGraph (C++ モック ビルド) および LangGraph (Python ツイン `langgraph_twin.py`) では、
同一の制約 (`--cpus=2 --memory=2g`) コンテナ内のメジャー。

```bash
OPENROUTER_API_KEY=... bash bench/run_bench.sh     # mock 200 turns + OpenRouter 20 turns × both
```

## 過去の測定結果 (2026-07-05、OpenRouter 移行前; Groq)

|メトリック |ネオグラフ |ランググラフ |デルタ |
|---|---|---|---|
|純粋なグラフのオーバーヘッド/ターン (モック 0ms LLM、200 ターン) | **0.38ms** | 3.07ミリ秒 | +2.7ms (8.1倍) |
| Groq リアル推論/ターン (80 ルーター + 700 シンセ、20 ターン) | 684ミリ秒 | 706ミリ秒 | +22ms (~3%) |
|グロク p99 | 775ミリ秒 | 870ミリ秒 | +95ms (n=20、ノイズマージン) |
|コールドスタート | 7.9ミリ秒 | 716ミリ秒 | ~90× |
| RSS (モック) | 7.5MB | 68MB | ～9倍 |

解釈：
- グラフ エンジン自体は、両側で LLM と比較して安価です (0.4 ミリ秒対 3 ミリ秒)。 Groq デルタ +22ms の
  ~19ms は HTTP クライアント スタックの違いです (langchain-openai httpx+pydantic と asio)。
- ターン間のギャップは **成長型** — 推論が高速化するにつれて大きくなります — 10% 以上
  200ms ターン (Cerebras レベル / シングルコール パス)、ローカルの小規模モデルの場合は 20 ～ 30% (~50ms/コール)。
- 90 倍の起動と 9 倍の RSS は、推論速度とは無関係の **固定ギャップ** です - すぐに
  エッジの常時オン、コールドスタート、マルチテナント (100 JARVIS = <1GB) に関連します。

低い絶対レイテンシ** (ローカル推論、同一データセンター推論) — それだけではありません

## 境界測定ラウンド — プロバイダーの分散を排除する (2026-07-05)

```bash
OPENROUTER_API_KEY=... bash bench/run_bench_proxy.sh
```

プロキシ境界測定を使用して E2E の「分散がデルタを飲み込む」問題を解決します。
**Groq の前に nginx を配置して **通話ごとのアップストリーム (WAN+Groq) 時間を記録**し、
残差のみを比較 (グラフ + HTTP クライアント シリアル化 + ローカル MCP + パイプ)
往復ターン数から減算後。統計的な回避策ではありません (増加
ABBA/再試行回数）ただし、ノイズ源自体を測定して減算する - 結果
たとえ弾が異なるGroqウィンドウに当たってもぐらつきません。

| |平均/ターン上流 | **残留 p50** |残留p90 |残存最小～最大 |
|---|---|---|---|---|
|ネオグラフ | 1613ミリ秒 | **3.5ミリ秒** | 19.1ミリ秒 | 1.9～80.5 |
|ランググラフ | 1417ミリ秒 | **14.7ミリ秒** | 25.1ミリ秒 | 10.8～33.3 |

- 生の壁時計は、今回は「LG の方が 189 ミリ秒速い」ことを示しています (Groq は NG ラウンドを悪化させました)
  ウィンドウ — アップストリーム平均 +196ms)。残差は **NG は p50 −11.1ms** を示します — クリア
  この方法がノイズの方向に関係なく信号を復元することを実証します。
- 残留 p50 は模擬ラウンド予測と一致します (グラフ 0.4 対 3.1 ミリ秒 + HTTP スタック差分) —
  ペイロードの相互検証が成功しました。
- コール↔ターンのマッピングは**順序ベース**です（コール数 = 2×ターン数、ログ順序 = ターン順序を確認します）。
  タイム ウィンドウ マッピングには、WSL2 ウォールクロック ステップ (実行中に -0.8 秒の反転を測定) があります。
  フォールバックのみ。ドライバーのタイムスタンプも単調アンカーから派生します。
- トラップメモ: Groq(Cloudflare) は `Python-urllib` UA を 403 でブロックします - 間違いやすいです
  プロキシ問題の場合。実際のスモーク テストは、curl/httpx ファミリー UA を使用します。

## ストリーミング TTFT ラウンド (2026-07-05)

最新の LLM サービスはすべてストリーミングであるため、ベンチマークが一致します: 両方のシンセ コールがストリーミングに変更されました
(C++ `invoke(p, on_chunk)`、LangGraph `SYNTH_LLM.stream()`)、
ドライバーは、`[jarvis:ttft]` マーカーを使用して **ターン送信→最初のシンセ トークン** 時間を測定します。
nginx は `proxy_buffering off` で SSE を通過させるため、`$upstream_header_time` は
本当の最初のバイト。ラウンドごとに個別のログ (mv + `nginx -s reopen`) を排除する
ラウンド分割の推測。

| |知覚されたTTFT p50 |完了時間 p50 |平均/ターン上流 |
|---|---|---|---|
|ネオグラフ | **631ms** | 744ミリ秒 | 726ミリ秒 |
|ランググラフ | **629ms** | 723ミリ秒 | 753ミリ秒 |

- **TTFT は実質的に同程度であると認識されました (デルタ -2ms)。** NeoGraph の方が明らかに遅い TTFT
  以前 (800 対 603) は純粋なプロバイダーの分散でした。今回は Groq が両方を提供しました
  フェアウィンドウ（上り 726 対 753）によりギャップが解消されます。 「NGラウンドのみ運が悪い」を確認
  生殖の疑い。
- **完了時間の残差 (純粋なフレームワーク) の再現**: NeoGraph 4.1ms 対 LangGraph
  14.6 ミリ秒 (以前のプロキシ ラウンド 3.5 対 14.7 と一致)。フレームワークのオーバーヘッド
  結論はしっかりしています。
- **TTFT-residual は ±数十 ms ノイズ以内で 0** (負の値も表示されます)。に比べ
  知覚 TTFT 625ms 対アップストリーム合計 673ms、2 を差し引いた分解能 (±50ms)
  独立したクロック (クライアントの単調性と nginx ウォールクロック) がフレームワークよりも大きい
  貢献度 (ミリ秒)。つまり、**フレームワークの違いは TTFT パスの観測限界を下回っています**
  — 信号は合計残差/モックでのみノイズの上に現れます。
- **ストリーミングの利点**: 知覚された TTFT (631) ≪ 完了時間 (744) — ユーザーが聞き始める
  0.6秒で答えます。待機する非ストリーミングよりも体感速度が向上することを確認
  完成のために。

概要: フレームワークの純粋なパフォーマンスが NeoGraph に有利 (合計残差・モック、再現可能)、
しかし、**TTFT はストリーミングに結びついており、プロバイダーの分散が支配的であると考えられています**。エッジ/マルチテナント
(90 倍の起動・9 倍の RSS) が依然として NeoGraph の本当の戦場です。

## 公平性の条件

- プロンプト (persona.txt 共有) · 意思決定検証 (チャット ダウングレード) · メモリ形式 (JsonFileStore) ·
  逐語的ガードと標準出力マーカーは同一です。フレームワークと言語のみが異なります。
- LangGraph 側は慣用的なスタック (langgraph + langchain-openai) を使用します。
- 測定はコンテナ内部の `driver.py` (標準入力 → `[jarvis:tts]` マーカーの往復) です。
