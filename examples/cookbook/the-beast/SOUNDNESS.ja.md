# コヒーレンスゲートの健全性 — 形式的な補足資料

**Languages:** [English](SOUNDNESS.md) | [한국어](SOUNDNESS.ko.md) | [日本語](SOUNDNESS.ja.md) | [简体中文](SOUNDNESS.zh-CN.md)

## 型付きプロバイダーへの移行 — エビデンスの境界

移行後のC++の作成／修復の経路は、型付きの `ProviderRequest` と `sp::Message` の履歴を組み立て、不変で完全な `sp::Outcome` の結果を受け取ります。返されたネイティブのメッセージとパートは、すべて対象になります。テキストを取り出すのは、候補のJSONやPythonをパースするときだけで、ネイティブの会話履歴の代わりに使うことはありません。コンパイル、パース、初期化のフィードバックは、それらのメッセージのあとに追加されます。意味レベルの修復の回数は、各プログラムの試行回数の上限で制限されます（ライブの作成は3回、Forgeサーバーの生成は2回）。トランスポートのリトライでも、無制限の進化でもありません。

interface 4の[Forgeのソース契約](README.md)は、これとは別に、空の `MaxTokens` からの回復を、上限を2倍にした呼び出し1回に制限しています。デッドラインは300秒に固定し、結果と使用量は保持します。失敗や、オブザーバー／精算のエラーを、リトライすることはありません。

プライベートなOpenRouterのルート `~deepseek/deepseek-v4-flash-latest` と `zdr: true` を維持してください（共有のサンプルのプロバイダーファクトリー）。ゼロデータ保持（ZDR）の条件を満たすエンドポイントがない場合は失敗します。データを保持するプロバイダーに、そのまま送られることはありません。ZDRのエンドポイント一覧は、データの所在地の保証でも、現時点で利用できることの証明でもありません。ライブで実行するには、承認されたキー、ネットワークとプロバイダーの可用性、有料の利用枠が必要です。プロンプト、エクスポートされたスキーマ、診断、ネイティブの履歴は、そのルートに送られます。生成されたPythonサーバーの実行には、ローカルでのコード実行に関する独自の信頼境界があり、NeoGraphのPythonプロバイダーバインディングとは別です。キーや非公開のプロンプトは、公開しないでください。null値になりうるトークンのカウンターは、ドルのコストではありません。料金と、実際に課金される使用量が前提になります。

保存してあるinterface 3の範囲を限定したランタイムのエビデンスが対象としているのは、実際のオフラインでのstrictなCoreのコンパイル、進化、チェックポイントのロールバックです。すべてのlive／apex／forge／scriptのバリエーションや、ベンダーの推論の適格性確認はできません。以下に残してあるコンソールの記録、ベンチマークとファジングの結果、ライブ実行についての記述は、過去のものであり、interface 4での測定ではありません。コヒーレンスゲートが確立するのは、記載された構造とエフェクト契約の性質です。プロバイダーのトランスポートやプライバシーの正しさ、モデルの意味的な真偽は、保証しません。PythonのプロバイダーバインディングはすでにTyped APIに移行しています。その検証は、これらのC++の実行とは別です。

これは、このクックブックにある実測用のハーネスの背景にある理論です。`gate_eval` は、ラベル付きのコーパスでコヒーレンスゲートが健全であることを*測定*しました。`gate_fuzz` は、数千のミュータントで*測定*して、その境界を明らかにしました。ゲートは、誠実なエフェクト契約に対しては健全で、偽りのある契約に対しては、ランタイムが最後の砦になります。この文書では、ハーネスの実行を表すスモールステップ操作的意味論と、ゲートが推論に使うエフェクト束の上で、対応する定理を*証明*します。

この証明が扱うのは、次の抽象機械です。リデューサーは全域的で、ノード本体は必ず値を返し、チャネルは宣言されたもので固定され、ディスパッチは全域的で静的にルーティングされるものとします。ノードやリデューサーの例外、キャンセル、プロバイダーやツールの失敗、リソースの上限、チェックポイントや保管のエラー、任意の生成コードは含みません。現在のC++エンジンには、これらの失敗モードもあります。引用している実装ファイルは、モデルの動機づけにしたものです。過去のコーパスで、C++の実装が機械的に検証されるわけではありません。このモデルの外側で、未定義動作が起きないことも示せません。

表記はASCIIで統一しています。`⊆ ∪ ∩ ∅` は集合演算、`⟨…⟩` は機械の構成、`↦` はマップの要素、`→` はステップ関係、`⊢ G ok` は整形式性の判定を表します。

## 1. 構文

ハーネス（コンパイル済みのグラフ）は、次のように表します。

    G = (N, E, D, ρ, R)

- `N`      — ノード名の有限集合です。特別な名前 `⊥s = __start__` と `⊥e = __end__` は、`N` に含まれません。
- `E ⊆ (N ∪ {⊥s}) × (N ∪ {⊥e})` — 静的なエッジです。
- `D`      — **宣言されたチャネル**（`channels` ブロック）の有限集合です。
- `ρ : N → 𝒫(Chan) × 𝒫(Chan)` — 各ノードの**エフェクト契約**です。`ρ(n) = (rd(n), wr(n))` と書き、ノードが読み取る、および書き込むと宣言したチャネルを表します。`Chan` はチャネル名全体の集合で、`D ⊆ Chan` です。
- `R`      — 条件付きノードのルーティングデータです。条件付きノード `n` では、`R(n)` はラベルからターゲットへの部分写像（ルートマップ）です。ラベルの集合を固定する、宣言された `ConditionSpec` が付くこともあります（省略可）。

バリア（ANDのjoinノード）は、`wait_for ⊆ N` の集合を持ちます。必要な箇所では、これを `G` に含めて考えます。

## 2. エフェクト束

エフェクトは、チャネルの冪集合の束の上で考えます。

    L = (𝒫(Chan), ⊆, ∪, ∩, ∅, Chan)

joinは `∪`、meetは `∩`、最小元は `∅`、最大元は `Chan` です。以降で使う性質は、次の2つです。

- **合成はjoinです。** 1つのスーパーステップでノードの集合 `F` を実行したときの書き込みエフェクトは、`⋃_{n∈F} wr(n)` です。各ノードの書き込みエフェクトの束のjoinにあたります。
- **単調性。** すべての `n` について `wr(n) ⊆ D` なら、すべての `F ⊆ N` について `⋃_{n∈F} wr(n) ⊆ D` が成り立ちます（joinは上界 `D` を保ちます）。

`D` は、`L` の中で注目する要素です。ステートが保持できるチャネルの集合を表します。

## 3. スモールステップ操作的意味論

**構成**は `⟨F, σ⟩` です。`F ⊆ N ∪ {⊥e}` はアクティブなフロンティア、`σ : D ↦ Val` はステートです。ステートは、宣言されたチャネルから値への全域写像で、各チャネル `c` にはリデューサー `⊕c` があります。実行は `⟨route(⊥s), σ0⟩` から始まり、`dom(σ0) = D` です。

ノード `n` を実行すると、書き込みリスト `⟦n⟧ = [(c1,v1), …, (ck,vk)]` が得られます。これは、実行時に*実際に*書き込まれるチャネルで、*宣言された*チャネルとは限りません。ステート更新の判定 `σ ⊢ W ⇒ σ'` は、書き込みリストを適用します。

                                           c ∈ D
    (Apply-ok)   ────────────────────────────────────────────────
                 σ ⊢ (c,v)::W  ⇒  σ[c ↦ σ(c) ⊕c v] ⊢ W ⇒ σ'

                                          c ∉ D
    (Apply-fault) ───────────────────────────────────────
                  σ ⊢ (c,v)::W  ⇒  ⊥                       (throws)

    (Apply-done)  σ ⊢ []  ⇒  σ

`(Apply-fault)` は、`c ∉ D` のときに `GraphState::write` や `apply_writes` が「Write to unknown channel」をスローする動作に、そのまま対応します。このモデルでは、`⊥` はフォルトの結果を表します。ステートの適用でフォルトしうるのはこの規則だけで、これがランタイムの書き込みガードです。

構成に対するスーパーステップの関係は、次のとおりです。

                 σ ⊢ (⋃_{n∈F} ⟦n⟧) ⇒ σ'        F' = route(F, σ')
    (Step)       ──────────────────────────────────────────────────
                 ⟨F, σ⟩  →  ⟨F', σ'⟩

                 σ ⊢ (⋃_{n∈F} ⟦n⟧) ⇒ ⊥
    (Step-fault) ─────────────────────────────
                 ⟨F, σ⟩  →  ⊥

    (Halt)       ⟨{⊥e}, σ⟩  →  ·          (terminates)

`route(F, σ')` は、たどったエッジとルート（および `goto` や `Send`）から、次のフロンティアを計算します。実行とは、`⟨F0,σ0⟩ → ⟨F1,σ1⟩ → …` という列のことで、`max_steps` が上限です。`{⊥e}` に到達すれば**終了**し、`⊥` に到達すれば**フォルト**します。どちらにもならずに `max_steps` ステップを実行した場合は、**ストール**します。

この抽象的な意味論には、構造に起因するディスパッチのフォルトが2つあります。

- **ぶら下がったルート（dangling route）。** `route` が、`m ∉ N ∪ {⊥e}` である名前 `m` へのエッジやルートをたどらなければならないとき、ディスパッチは未定義（ぶら下がった参照）です。これは `→ ⊥` としてモデル化します。
- **空のルートでのディスパッチ。** 条件付きノード `n` のルートマップが `R(n) = ∅` の場合、このモデルではディスパッチ先が得られません。これも `→ ⊥` としてモデル化します。

## 4. 整形式性の判定としてのゲート

`GraphValidator::validate` は、エラーと警告を返します。**エラー**は、拒否の条件そのものです。ゲートを通過するのは、エラーが1つもないときだけです。ここでは、4つのエラーのファミリー（E3、E4-write、E8、E10）を、`⊢ G ok` の前提として読みます。

    (E3)  ∀ (a,b) ∈ E.  a ∈ N ∪ {⊥s}  ∧  b ∈ N ∪ {⊥e}
          ∀ conditional n, label ℓ.  R(n)(ℓ) ∈ N ∪ {⊥e}
          ∀ barrier n, m ∈ wait_for(n).  m ∈ N
    (E4)  ∀ n ∈ N.  wr(n) ⊆ D                       -- declared writes are declared
    (E8)  ∀ barrier n, m ∈ wait_for(n).  ∃ static edge/route into n from m
    (E10) ∀ conditional n with a closed ConditionSpec of labels Λ.
              dom(R(n)) = Λ   (no dead keys, no uncovered labels)
          ∀ conditional n.  R(n) ≠ ∅

          ────────────────────────────────────────────────────────────
                                  ⊢ G ok

**警告**（E5の上書き競合、E6の使われないチャネル、E7の到達不能、E9の同期されていないfan-in、E11の終了までのパスがない、E4-readの未宣言のチャネルの読み取り）は、意図的に `⊢ ok` の前提には*含めていません*。第7節で示すとおり、どれもフォルトを起こしません。その不在を要求すると、安全なグラフまで拒否してしまいます（過剰な拒否）。これは設計上の選択で、カタログでは「カバレッジより健全性」と表現しています。

カバレッジについては、1つ注意が必要です。エフェクトのファミリー（E4／E5／E6）が実行されるのは、**すべての**ノードタイプが契約を宣言している場合だけです。契約が不明なタイプが1つでもあれば、無効になります。したがって、`(E4)` が `⊢ G ok` の前提になるのは、次の条件のもとだけです。

    (Cov)  every node in N has a declared effect contract ρ(n).

`(Cov)` がなければ、ゲートは書き込みをまったく見られないため、書き込みについての健全性は主張しません。以下の定理も同様です。

## 5. 誠実性の仮定

ゲートが推論するのは、*宣言された*エフェクト `wr(n)` です。ランタイムが実行するのは、*実際の*書き込み `⟦n⟧` です。この2つをつなぐのが、次の仮定です。

    (H)  ∀ n ∈ N.  channels(⟦n⟧) ⊆ wr(n)

つまり、どのノードも、宣言したチャネルにしか書き込みません。`(H)` はノードの実装についての仮定であり、静的なゲートでは検証できません。ノードの `run` は、中身が見えないC++だからです。`gate_fuzz` のレイヤー2には、`(H)` に違反するノード（`{out}` と宣言しながら、`phantom` に書き込む）が登場します。そのケースは、6.4で扱います。

## 6. 健全性

`⊢ G ok` と `(Cov)` を満たす `G` を固定します。`⟨route(⊥s), σ0⟩` から到達可能な構成の集合を、`Reach(G)` と書きます。

### 6.1 補題（定義域の不変条件）

*すべての `⟨F, σ⟩ ∈ Reach(G)` について、`dom(σ) = D` である。*

**証明。** 構成により、`dom(σ0) = D` です。`(Apply-ok)` が `σ[c ↦ …]` を更新するのは、前提により `c ∈ D` の場合だけです。そのため、定義域は保たれ、キーが追加されたり削除されたりすることはありません。`(Apply-fault)` が返すのは `⊥` で、ステートではありません。したがって、フォルトしないステップはすべて `dom(σ) = D` を保ちます。実行の長さについての帰納法により、この不変条件は最後まで成り立ちます。∎

### 6.2 補題（書き込みは宣言の範囲内に収まる）

*`(H)` を仮定する。到達可能なすべての `⟨F, σ⟩` と、すべての `n ∈ F` について、`channels(⟦n⟧) ⊆ D` である。*

**証明。** `(H)` により、`channels(⟦n⟧) ⊆ wr(n)` です。`⊢ G ok` の前提 `(E4)` により、`wr(n) ⊆ D` です（`(Cov)` が成り立つので、この前提が使えます）。推移律から `channels(⟦n⟧) ⊆ D` が得られます。`n ∈ F` についてjoinをとり、単調性（第2節）を使うと、`channels(⋃_{n∈F} ⟦n⟧) ⊆ D` が得られます。∎

### 6.3 定理（進行性／フォルトしないこと）

*`⊢ G ok`、`(Cov)`、`(H)` を仮定する。到達可能などの構成も、`⊥` にステップすることはない。どの実行も、終了する（`{⊥e}` に到達する）か、`max_steps` でストールするかのどちらかで、フォルトすることはない。*

**証明。** ステップが `⊥` に至るのは、`(Step-fault)`、ぶら下がったルート、空のルートでのディスパッチのいずれかの場合だけです。それぞれを排除します。

- **書き込みのフォルト `(Step-fault)`。** これが起きるには、`σ ⊢ (⋃_{n∈F} ⟦n⟧) ⇒ ⊥` となる必要があります。つまり、結合した書き込みリストに、`c ∉ D` である `(c,v)` が含まれることになります。補題6.2により、`channels(⋃_{n∈F} ⟦n⟧) ⊆ D` なので、そのような `c` は存在しません。`(Apply-fault)` が有効になることはなく、すべての適用は、`(Apply-ok)` と `(Apply-done)` によって、状態 `σ'` に簡約されます（補題6.1により `dom(σ') = D` です）。これは矛盾です。

- **ぶら下がったルート。** `route` がたどるのは、エッジ `(a,b) ∈ E`、ルートのターゲット `R(n)(ℓ)`、バリアのメンバーのいずれかです。前提 `(E3)` により、`b ∈ N ∪ {⊥e}`、`R(n)(ℓ) ∈ N ∪ {⊥e}`、そしてバリアのメンバーはすべてNの要素（`∈ N`）です。したがって、たどるターゲットは、必ず既存のノードか `⊥e` を指しており、ディスパッチは定義されています。

- **空のルートでのディスパッチ。** そのためには、`R(n) = ∅` の条件付きノード `n` に到達する必要があります。前提 `(E10)` により、すべての条件付きノードで `R(n) ≠ ∅` です。したがって、この場合は起こりません。

到達可能などの構成でも、`⊥` に至る規則は有効になりません。これ以外のステップ関係は全域的です（スーパーステップは、必ず次のフロンティアを生成します）。したがって、すべての実行は、フォルトしないステップが無限に続く列か、終了する列で、`max_steps` で打ち切られます。つまり、実行は終了するかストールするかのどちらかで、フォルトすることはありません。∎

`(E8)` が検査するのは、バリアのメンバーに宣言された、静的な入力エッジとルートです。すべてのメンバーが実行されることまでは証明しません。排他的なルートがあると、ANDのjoinが発火しないことがあります。この証明では、バリアの活性（liveness）は確立しません。すべてのデッドロックを、意図したサイクルと区別することもしません。抽象モデルの中でフォルトしないことは、終了の保証を必要としません。

### 6.4 系（誠実な契約を前提としたゲートの健全性）

*ゲートを通過し（`⊢ G ok`）、契約が完全にカバーされ（`(Cov)`）、すべての契約が誠実（`(H)`）であるなら、実行はフォルトしない。宣言されていないチャネルへの書き込みも、ぶら下がったルートや空のルートでのディスパッチのフォルトも起こらない。*

このモデルで成り立つ含意は `gate-pass ⟹ no-modeled-fault` です。その対偶は `modeled-fault ⟹ gate-reject` であって、`gate-reject ⟹ fault` ではありません。過去のコーパスで検査したのは、拒否された特定の例です。拒否されたものがすべてフォルトすることまでは、証明していません。保存してあるファジングの結果では、2000個のミュータントのうち、ゲートを通過したあとにフォルトしたものはありませんでした。

### 6.5 命題（`(H)` は必要であり、ランタイムが最後の砦になる）

*`(H)` がなければ、`⊢ G ok` はフォルトしないことを含意しない。ただし、合成したシステム（ゲートとランタイムのガード）は、それでもフェイルストップである。未定義動作には至らず、明確な `⊥` で止まる。*

**証明。** *必要性。* `G` を、コヒーレントなシードに、ノード `n` を加えたものとします。ノード `n` は、`ρ(n) = ({}, {out})`、`out ∈ D` ですが、`⟦n⟧ = [(phantom, 1)]`、`phantom ∉ D` とします。`⊢ G ok` の前提はすべて成り立ちます（特に `(E4)` は、`wr(n) = {out} ⊆ D` です）。そのため、ゲートは通過します。しかし、`n` を実行すると、`phantom` に対して `(Apply-fault)` が起き、実行はフォルトします。したがって、`(H)` が成り立たないときは、`⊢ G ok ⇏ non-fault` です（これはまさに、`gate_fuzz` のレイヤー2にある、偽りの宣言をするノードで、500回中500回でした）。

*フェイルストップ。* 違反は、`(Apply-fault)` 自体によって捕捉されます。これは、定義された決定的な `throw` で、未定義動作ではありません。そのため、`(H)` が成り立たなくても、実行がステートを壊したり、未定義動作に暴走したりすることはありません。診断を出して停止します。静的なゲートが仮定せざるを得ない唯一の仮定について、ランタイムの書き込みガードが、健全な最後の砦になっています。∎

この2つを合わせると、システム全体について述べるべき、*無条件の*安全性の主張になります。

> **静的なゲートは、誠実なエフェクト契約を前提とすれば健全である（定理6.3／系6.4）。ランタイムの書き込みガードにより、契約が偽りであっても、実行はフェイルストップになる（命題6.5）。`⊢ G ok` のもとで到達可能な構成は、この抽象機械の中で、述べた仮定のもとでは、どれも未定義動作を起こさない。**

## 7. 警告が前提に含まれない理由

（過剰な拒否がないことを示す意味で）念のために、各警告のクラスが、進行性にとって無害であることを示します。これが、`⊢ G ok` から除外する理由です。

- **E7（到達不能なノード）、E11（`__end__` へのパスがない）。** 到達不能なノードは、到達可能なフロンティア `F` に現れることがありません。そのため、書き込みもルーティングも行わず、フォルトすることもありません（定理6.3が量化しているのは、`n ∈ F` だけです）。E11が関わるのは終了であり、フォルトではありません。
- **E9（同期されていないfan-in）、E5（上書き競合）。** チャネルの*値*が、スーパーステップへの到着順に依存します（非決定性）。しかし、すべての書き込みは、依然として `c ∈ D` を対象とします（補題6.2には影響しません）。そのため、フォルトしません。リデューサー `⊕c` は全域的です。順序への依存はセマンティクス上の危険であり、行き詰まったステートではありません。
- **E6（使われないチャネル）。** 宣言されているが書き込まれないチャネルは、初期値のままです。その読み取りは、定義域の中の値を返します。フォルトしません。
- **E4-read（未宣言のチャネルの読み取り）。** `null` を返すものとしてモデル化します（コードは、読み取りでは例外を投げずに、null値を返します）。フォルトしません。そのため、E4-writeとは違って、エラーではなく警告です。

どれも実際に意味のある性質ですが、`→ ⊥` を引き起こすことはありません。これらを禁止すると、安全なハーネスまで拒否することになるので、ゲートは警告として扱います。これが、カタログで言う「カバレッジより健全性」の形式的な内容です。

## 8. 範囲と、正直に述べておく限界

- **終了性ではありません。** ここでの健全性は、*フォルトしないこと*であり、*終了すること*ではありません。サイクルは正当なもの（`goto` や `Send` によるループ）で、`max_steps` まで実行されてストールします。定理が述べているのは、ゲートを通過したグラフが*例外を投げたり*、*未定義動作*に陥ったりしないことで、停止することではありません。`gate_fuzz` がストールをフォルトとして扱わないのは、まさにこのためです。
- **抽象化の忠実さ。** 証明の対象は、第3節のモデルです。このモデルはコードを写したものですが、コードから抽出したものではありません。実測用のハーネスが、忠実さの検査になります。ハーネスと定理の間に食い違いがあれば、モデル（またはコード）がずれたことを示します。`gate_fuzz` のレイヤー1が、常設の回帰ガードです。
- **カバレッジ `(Cov)`。** 書き込みの健全性（E4）を主張するのは、すべてのノードタイプが契約を宣言している場合だけです。「未知のタイプが1つでもあれば、そのファミリーは無効になる」というゲートの動作と対応しています。カバレッジが部分的なときは、ゲートは何も言わず、定理も何も言いません。
- **誠実性 `(H)`。** 仮定であり、必要であり（命題6.5）、ランタイムが最後の砦になります。特定のノードについて `(H)` を機械的に証明するには、その `run` の本体の検証が必要です。ここでは範囲外とし、書き込みガードで現実的に代替しています。
- **静的なルーティングだけ。** 前提 `(E3)` が制約するのは、*静的な*エッジ、ルート、バリアの構造です。そのため、定理6.3のぶら下がったルートの場合は、ゲートが見えるターゲットだけを対象にします。`Command.goto` や `Send` は、ターゲットを*実行時の値*として計算します（E7の到達可能性が、エラーではなく警告なのは、まさにこのためです）。このような動的なターゲットは、静的なゲートからは見えません。書き込みにおける `(H)` と同じ形の隙間で、スケジューラーが実行時に扱う問題です。この定理の主張には含まれません。証明の範囲は、静的にルーティングされるディスパッチです。動的なルーティングも、同様に、実行時に検査されます。
