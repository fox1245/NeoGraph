# 一致性门控的健全性——一个形式化伴随文档

**Languages:** [English](SOUNDNESS.md) | [한국어](SOUNDNESS.ko.md) | [日本語](SOUNDNESS.ja.md) | [简体中文](SOUNDNESS.zh-CN.md)

这是本 cookbook 中经验执行框架背后的理论。`gate_eval` 在有标签语料库上
*测量*了一致性门控的健全性；`gate_fuzz` 在数千个突变体上*测量*了它，
并描绘了它的边界（相对于诚实效果契约是健全的，并为不诚实契约提供运行时后备）。
本文档在执行框架执行的小步操作语义以及门控所推理的效果格上，*证明*对应的定理。

这是对真实引擎的**忠实抽象**所作的证明：它精确建模了代码实现的
超级步语义和通道写保护（`src/core/graph_state.cpp`、`src/core/graph_engine.cpp`、
`src/core/graph_validator.cpp`），但不会逐行机械验证 C++。
抽象的保真度正由 `gate_eval` 和 `gate_fuzz` 佐证：定理的预测与它们运行的每个案例一致。
证明 + 实测模型，这正是本项目自我要求的方法。

符号为 ASCII：`⊆ ∪ ∩ ∅` 是集合运算； `⟨…⟩`机器配置；
`↦`映射项； `→`阶跃关系； `⊢ G ok`良构性判断。

---

## 1. 语法

一个执行框架（编译图）是
    G = (N, E, D, ρ, R)

- `N` — 节点名称的有限集。两个特殊名称 `⊥s = __start__` 和
             `⊥e = __end__` 不在 `N` 中。
- `E ⊆ (N ∪ {⊥s}) × (N ∪ {⊥e})` — 静态边。
- `D` — **声明的通道**的有限集（`channels`块）。
- `ρ : N → 𝒫(Chan) × 𝒫(Chan)` — 每个节点的**效果契约**，写作
             `ρ(n) = (rd(n), wr(n))`：节点声明自己读取和写入的通道。
             `Chan` 是通道名的全集；`D ⊆ Chan`。
- `R` — 条件节点的路由数据：对于条件节点`n`，
             `R(n)`是从标签到目标的部分映射（路由表），加上
             可选声明的 `ConditionSpec` 固定其标签集。

屏障（AND-join 节点）带有 `wait_for ⊆ N` 集。我们将它们折叠到 `G` 中
在需要的地方。

## 2. 效果格

效果位于通道上的幂集格中
    L = (𝒫(Chan), ⊆, ∪, ∩, ∅, Chan)

与上确界`∪`，下确界 `∩`，底 `∅`，顶 `Chan`。我们使用两个事实：

- **组合是上确界。** 在一个超级步中运行节点集合 `F` 的写入效果是
  `⋃_{n∈F} wr(n)`，也就是这些写入效果的格上确界。
- **单调性。** 如果 `wr(n) ⊆ D` 对于每个 `n`，则 `⋃_{n∈F} wr(n) ⊆ D` 对于
  每个`F ⊆ N`（上确界保留上限`D`）。

`D` 是`L` 的相关元素：状态可以保存的通道集。

## 3. 小步操作语义

**配置**是 `⟨F, σ⟩`，其中 `F ⊆ N ∪ {⊥e}` 是活动边界，并且
`σ : D ↦ Val`是状态（从声明的通道到值的总映射；
每个通道`c`都有一个归约器`⊕c`)。执行从 `⟨route(⊥s), σ0⟩` 开始
`dom(σ0) = D`。

运行节点 `n` 会生成一个写入列表 `⟦n⟧ = [(c1,v1), …, (ck,vk)]` —
它*实际上*在运行时写入的通道（不一定是它*声明的*）。
状态更新判断`σ ⊢ W ⇒ σ'`应用写入列表：
                                           c ∈ D
    (Apply-ok)   ────────────────────────────────────────────────
                 σ ⊢ (c,v)::W  ⇒  σ[c ↦ σ(c) ⊕c v] ⊢ W ⇒ σ'

                                          c ∉ D
    (Apply-fault) ───────────────────────────────────────
                  σ ⊢ (c,v)::W  ⇒  ⊥                       (throws)

    (Apply-done)  σ ⊢ []  ⇒  σ

`(Apply-fault)` 正是 `GraphState::write` / `apply_writes` 投掷
`c ∉ D` 时“写入未知通道”(graph_state.cpp:59–92)。 `⊥` 是
故障结果——抛出异常。这是*唯一*可能出错的规则
状态应用，它是运行时写保护。

配置上的超步关系：
                 σ ⊢ (⋃_{n∈F} ⟦n⟧) ⇒ σ'        F' = route(F, σ')
    (Step)       ──────────────────────────────────────────────────
                 ⟨F, σ⟩  →  ⟨F', σ'⟩

                 σ ⊢ (⋃_{n∈F} ⟦n⟧) ⇒ ⊥
    (Step-fault) ─────────────────────────────
                 ⟨F, σ⟩  →  ⊥

    (Halt)       ⟨{⊥e}, σ⟩  →  ·          (terminates)

`route(F, σ')` 从所采取的边/路线（以及任何
`goto`/`Send`)。一次游程是序列 `⟨F0,σ0⟩ → ⟨F1,σ1⟩ → …`，其边界为
`max_steps`；如果它达到`{⊥e}`，它**终止**，如果它达到`⊥`它
**故障**，如果它运行`max_steps`步骤而没有任何一个，它就会**停止**。

语义可以展示另外两种运行时故障模式，与代码相匹配：

- **悬空路线。** 如果`route`必须沿着边/路线到达名称`m ∉ N ∪
  {⊥e}`，则调度未定义（悬空引用）。将其建模为`→ ⊥`。
- **空路由调度。** 如果条件节点`n`有路由图`R(n) = ∅`，
  调度器取消引用空容器的反向端
  （`rend()`，UB）。将其建模为`→ ⊥`。

## 4. 门作为良构性判断

`GraphValidator::validate` 返回错误和警告。**错误**正是拒绝条件；
当且仅当没有错误时，门控通过。我们把四个错误家族（E3、E4-write、E8、E10）
读作 `⊢ G ok` 的前提：
    (E3)  ∀ (a,b) ∈ E.  a ∈ N ∪ {⊥s}  ∧  b ∈ N ∪ {⊥e}
          ∀ conditional n, label ℓ.  R(n)(ℓ) ∈ N ∪ {⊥e}
          ∀ barrier n, m ∈ wait_for(n).  m ∈ N
    (E4)  ∀ n ∈ N.  wr(n) ⊆ D                       -- declared writes are declared
    (E8)  ∀ barrier n, m ∈ wait_for(n).  ∃ static edge/route into n from m
    (E10) ∀ conditional n with a closed ConditionSpec of labels Λ.
              dom(R(n)) = Λ   (no dead keys, no uncovered labels)
          ∀ conditional n.  R(n) ≠ ∅

          ────────────────────────────────────────────────────────────
                                  ⊢ G ok

**警告**（E5 覆盖竞争、E6 死通道、E7 无法访问、E9
不同步扇入、E11 没有到 `__end__` 的路径、E4 未声明的读取）是
故意*不*`⊢ ok`的前提：§7表明它们都不能导致故障，所以
要求他们缺席将拒绝安全图（过度拒绝）。这是一个
目录中说明的设计选择称为“健全性高于覆盖范围”。

诚实呈现的一项覆盖范围注意事项：仅运行效果系列 (E4/E5/E6)
当**每个**节点类型声明合约时；单一未知合约类型
禁用它。所以 `(E4)` 是 `⊢ G ok` 的前提
    (Cov)  every node in N has a declared effect contract ρ(n).

如果没有 `(Cov)`，门根本看不到写入并且不会产生写入健全性
断言——下面的定理也没有断言。

## 5. 诚实假设

门对*声明*效果的原因`wr(n)`；运行时执行*实际*
写入`⟦n⟧`。这座桥是：
    (H)  ∀ n ∈ N.  channels(⟦n⟧) ⊆ wr(n)

即每个节点只写入它声明的通道。 `(H)` 是关于
节点实现，静态门无法验证 - 节点的`run`
是不透明的C++。 `gate_fuzz` 第 2 层展示了一个违反`(H)` 的节点（声明
`{out}`，写入`phantom`)； §6.4 处理这种情况。

## 6. 健全性

将`G` 与`⊢ G ok` 和`(Cov)` 一起修复。为集合写`Reach(G)`
可通过`⟨route(⊥s), σ0⟩`进行配置。

### 6.1 引理（域不变量）

*对于每个 `⟨F, σ⟩ ∈ Reach(G)`、`dom(σ) = D`.*

**证明。** `dom(σ0) = D` 通过构造。 `(Apply-ok)`仅更新`σ[c ↦ …]`
对于`c ∈ D`（其前提），因此它保留了域；它从不添加或删除
关键。 `(Apply-fault)` 产生`⊥`，而不是一个状态。因此每一个无错误的步骤
保留`dom(σ) = D`。通过游程长度归纳，不变量成立
整个过程。 ∎

### 6.2 引理（写入保持声明状态）

*假设`(H)`。对于每个可到达的`⟨F, σ⟩`和每个`n ∈ F`，
`channels(⟦n⟧) ⊆ D`.*

**证明。** `channels(⟦n⟧) ⊆ wr(n)` 由 `(H)` 得出。 `wr(n) ⊆ D` 的前提 `(E4)`
`⊢ G ok`（可用，因为`(Cov)`成立）。传递性给出
`channels(⟦n⟧) ⊆ D`。取 `n ∈ F` 的上确界（并），单调性 (§2) 给出
`channels(⋃_{n∈F} ⟦n⟧) ⊆ D`。 ∎

### 6.3 定理（进步/非错误）

*假设`⊢ G ok`、`(Cov)`和`(H)`。没有可达到的配置步骤`⊥`。
每次运行要么终止（到达`{⊥e}`），要么停止在`max_steps`；它从来没有
错误。*

**证明。** 一个步骤只能通过 `(Step-fault)`、悬空路线或一条路径到达 `⊥`
空路线调度。我们排除每一个。

- **写故障`(Step-fault)`.** 这需要`σ ⊢ (⋃_{n∈F} ⟦n⟧) ⇒ ⊥`，即
  与 `c ∉ D` 组合的写入列表中的一些`(c,v)`。根据引理 6.2，
  `channels(⋃_{n∈F} ⟦n⟧) ⊆ D`，因此不存在这样的`c`。 `(Apply-fault)`从来都不是
  已启用；每个应用程序都会减少 `(Apply-ok)`/`(Apply-done)` 到一个状态
  `σ'`（与引理 6.1 的`dom(σ') = D`）。矛盾。

- **悬空路线。** `route` 遵循边 `(a,b) ∈ E` 或路线目标
  `R(n)(ℓ)` 或屏障成员。前提`(E3)`给出`b ∈ N ∪ {⊥e}`，
  `R(n)(ℓ) ∈ N ∪ {⊥e}`，以及每个屏障成员`∈ N`。所以每个跟随的目标
  命名现有节点或`⊥e`； 调度已定义。

- **空路由调度。** 需要通过 `R(n) = ∅` 达到条件`n`。
  前提 `(E10)` 为每个条件节点提供 `R(n) ≠ ∅`。排除。

在任何可到达的配置中都不会启用`⊥` 的规则。由于阶跃关系
否则是总计（超级步骤总是产生下一个边界），每次运行都是
无限或终止的非故障步骤链，在`max_steps`处截断。
因此它终止或停止，永远不会出现故障。 ∎

关于`(E8)`的注释：屏障活性是防止“失速”掩盖*错误*的原因。安
不可满足的 AND-上确界（没有静态路径的 `wait_for` 成员）永远不可能
火，困跑进了一个档位那真是一个僵局。 `(E8)`禁止它，
因此`⊢ G ok`下的失速反映了真正的循环（受`max_steps`限制），而不是
结构上死的屏障。进步（非过失）并不取决于此；它
加深了失速结果的意义。

### 6.4 推论（门的健全性，相对于诚实合约）

*如果大门通过（`⊢ G ok`）并具有完整的合同覆盖`(Cov)`，并且所有
合同是诚实的`(H)`，那么执行不会出错：不写入
未声明的通道，无悬空路由或空路由 UB。*

这就是执行框架衡量的定理。 `gate_eval`的`validator-error ⟹
runtime-fault`是其标记语料库上的反证； `gate_fuzz`第1层
是它的统计阴影：超过 2000 个突变体，`⊢ G ok`图从未出现过错误。

### 6.5 命题（`(H)`是必要的；运行时是后盾）

*没有`(H)`，`⊢ G ok`并不意味着无过失——但复合系统
（门+运行时防护）仍然是故障停止：它永远不会达到未定义行为，
只有干净的`⊥`.*

**证明。** *必要性。* 取 `G` = 一个连贯的种子加上一个节点 `n`
`ρ(n) = ({}, {out})`、`out ∈ D`，但`⟦n⟧ = [(phantom, 1)]`、`phantom ∉ D`。
`⊢ G ok` 的每个前提都成立（特别是 `(E4)`: `wr(n) = {out} ⊆ D`），所以
门过去了。然而，运行 `n` 会在 `phantom` 上触发 `(Apply-fault)`，因此
运行故障。因此，当 `(H)` 失败时，`⊢ G ok ⇏ non-fault`。 （这正是
`gate_fuzz` 第 2 层所在节点，500/500。）

*故障停止。*违规行为由 `(Apply-fault)` 本身捕获 - 一个已定义的、
确定性的`throw`，而不是未定义的行为。所以即使没有`(H)`，执行
不能破坏状态或进入 UB：它会因诊断而停止。运行时
因此，写保护是静态门这一假设的可靠后盾
必须假设。 ∎

两者共同给出了*无条件*的安全声明，这是诚实的
关于整个系统的一件事：

> **静态门相对于诚实的效果契约来说是合理的（Thm 6.3 /
> Cor 6.4）。运行时写保护使执行失败停止，即使
> 合同谎言（提案 6.5）。 `⊢ G ok` 展品下无法进行配置
> 未定义行为。**

## 7. 为什么警告不是前提

为了完整性（在“没有过度拒绝”的意义上），显示了每个警告范畴
对进步无害——证明其被排除在`⊢ G ok`之外是合理的：

- **E7（无法到达的节点）、E11（没有通往 `__end__` 的路径）。** 无法到达的节点是
  永远不会在任何可到达的边界`F`中，因此它不贡献任何写入和路由
  — 它不会出错（Thm 6.3 仅对 `n ∈ F` 进行量化）。 E11 关注
  终止，而非故障。
- **E9（不同步扇入）、E5（覆盖竞争）。**这些使得*值*
  通道取决于超步到达顺序（不确定性），但每次写入
  仍然以`c ∈ D`为目标（引理 6.2 不受影响），所以没有错误。归约器
  `⊕c` 是全部。顺序依赖性是一种语义风险，而不是卡住状态。
- **E6（死通道）。** 已声明但未写入的通道保留其初始值
  价值；读取它会产生域内的值。没有错。
- **E4-read（读取未声明的通道）。** 建模为产生`null`（代码
  返回一个空值，它不会在读取时抛出）。没有错误——因此发出警告，
  与 E4-write 不同，这不是错误。

每个都是真正的语义属性，但没有一个可以驱动`→ ⊥`；禁止他们会
拒绝安全执行框架，因此门将它们保留为警告。这是正式的
目录的内容“健全性超过覆盖范围”。

## 8. 范围和诚实限制

- **不是终止。** 这里的健全性是*非故障*，而不是*终止*。周期
  是合法的（通过`goto`/`Send`循环）并运行到`max_steps` → 停顿。的
  定理说，过门图永远不会*抛出*或击中*UB*，但事实并非如此
  停止。正是出于这个原因，`gate_fuzz` 将失速视为非过失。
- **抽象保真度。** 证明是基于§3的模型，它反映了
  代码，但未从中提取。经验执行框架是保真度
  检查；它们与定理之间的分歧将表明模型（或
  代码）漂移 — `gate_fuzz` 第 1 层是常设回归守卫。
- **覆盖范围`(Cov)`.** 仅当每种节点类型时才声明写入健全性 (E4)
  宣布签订合同，反映“一种未知类型使家庭丧失能力”
  门。在部分覆盖下，门是沉默的，定理也是如此。
- **诚实`(H)`.** 假设的、必要的（提案 6.5），并在运行时得到支持。
  特定节点的 `(H)` 的机械化证明需要验证其
  `run` 主体 — 超出此处的范围；写保护是实用的替代品。
- **仅静态路由。**前提`(E3)`约束*静态*边/路由/
  屏障结构，因此 Thm 6.3 的悬空路线情况涵盖了目标
  门可以看到。 `Command.goto`/`Send` 将其目标计算为*运行时值*
  （这正是 E7 可达性是警告而不是错误的原因）。这样的动态
  目标位于静态门视野之外 - 间隙形状与`(H)`相同
  用于写入 - 是调度器的运行时问题，而不是对此的声明
  定理。证明范围为静态路由调度；动态路由是
  类似地进行运行时检查。
