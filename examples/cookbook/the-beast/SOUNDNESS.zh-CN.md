# 一致性闸门的健全性：一份形式化的配套文档

**Languages:** [English](SOUNDNESS.md) | [한국어](SOUNDNESS.ko.md) | [日本語](SOUNDNESS.ja.md) | [简体中文](SOUNDNESS.zh-CN.md)

## 带类型 provider 迁移：证据边界

迁移后的 C++ 编写与修复路径，会构造带类型的 `ProviderRequest` 和 `sp::Message` 历史，并消费完整、不可变的 `sp::Outcome` 结果，其中包括返回的每一条原生消息和每个 part。提取文本只是为了解析候选的 JSON/Python，不会用它替换原生的对话历史。编译、解析、初始化的反馈，会追加在这些消息之后。语义修复受每个程序自身的尝试次数限制（实时编写：三次；Forge 服务器生成：两次）；它既不是传输层重试，也不是不受限制的演化。

interface-4 的 [Forge 源码契约](README.md)另外规定：遇到空的
`MaxTokens` 时，最多只做一次把上限加倍的恢复调用，截止时间固定为 300 秒，并保留 outcome 和用量；
对失败以及 observer/settlement 错误，它从不重试。

保持使用私有的 OpenRouter 路由 `~deepseek/deepseek-v4-flash-latest`，并设置 `zdr: true`（共用的示例 provider 工厂）：如果没有符合条件的零数据留存 endpoint，就直接失败，而不是把数据披露给会留存数据的 provider。ZDR endpoint 清单既不保证数据驻留，也不证明当前可用。实时执行需要有授权的密钥、可用的网络和 provider，以及付费额度；提示词、导出的 schema、诊断信息和原生历史都会发送到这条路由。生成的 Python 服务器在本地执行代码，有它自己的信任边界，与 NeoGraph 的 Python provider 绑定无关。切勿公开密钥或私有提示词。可为空的 token 计数不等于美元费用；要算费用，需要有定价，以及实际计费的用量。

保留下来的 interface-3 限定范围的运行时证据，覆盖实际的离线 strict Core 编译、演化和检查点回滚。它不能证明所有 live/apex/forge/script 变体，也不能证明供应商的推理服务合格。下文保留的控制台记录、基准测试/fuzz 结果和实时执行的说法，仍然是历史数据，不是 interface-4 的测量值。一致性闸门只能确立它所声明的结构/效果契约性质，不能确立 provider 传输和隐私方面的正确性，也不能确立模型输出在语义上的真实性。Python provider 绑定现在遵循带类型的 API；它们的验证与这些 C++ 运行是分开的。

这是本 cookbook 中各个经验性测试工具背后的理论。`gate_eval` 在带标签的语料库上
*测量*了这道一致性闸门是健全的；`gate_fuzz` 在数千个变异体上*测量*了它，
并划出了它的边界（相对于诚实的效果契约，它是健全的；对不诚实的契约，另有运行时兜底）。
本文档则在 harness 执行的小步操作语义，以及闸门所推理的效果格上，
*证明*相应的定理。

证明针对下面这台抽象机：reducer 都是全函数，节点体都会返回，通道是固定声明好的，
分发是全函数且由静态路由决定。它不包括节点/reducer 抛出异常、取消、provider/工具失败、
资源上限、检查点/托管(custody)错误，以及任意生成的代码；而当前的 C++ 引擎存在这些额外的失败模式。
文中引用的实现文件只是这个模型的依据；历史语料库既不能机械地验证 C++ 实现，
也不能确立在该模型之外没有未定义行为。

记号约定：`⊆ ∪ ∩ ∅` 是集合运算；`⟨…⟩` 是机器配置；
`↦` 是映射项；`→` 是步进关系；`⊢ G ok` 是良构性判断。

## 1. 语法

一个 harness（编译后的图）是

    G = (N, E, D, ρ, R)

- `N`      — 节点名称的有限集合。另有两个特殊名称 `⊥s = __start__`
             和 `⊥e = __end__`，它们不属于 `N`。
- `E ⊆ (N ∪ {⊥s}) × (N ∪ {⊥e})` — 静态边。
- `D`      — **声明的通道**（`channels` 块）构成的有限集合。
- `ρ : N → 𝒫(Chan) × 𝒫(Chan)` — 每个节点的**效果契约**，记作
             `ρ(n) = (rd(n), wr(n))`：即该节点声明自己会读、会写的通道。
             `Chan` 是全体通道名的集合；`D ⊆ Chan`。
- `R`      — 条件节点的路由数据：对条件节点 `n`，
             `R(n)` 是从标签到目标的偏映射（路由表），另外还可以带一个
             声明的 `ConditionSpec`，用来固定它的标签集合。

屏障（AND-join 节点）带有一个 `wait_for ⊆ N` 集合。需要时，我们把它并入 `G`。

## 2. 效果格

效果位于通道上的幂集格中

    L = (𝒫(Chan), ⊆, ∪, ∩, ∅, Chan)

其中并为 `∪`，交为 `∩`，底元为 `∅`，顶元为 `Chan`。我们用到两个事实：

- **组合就是并。** 在一个超步里运行节点集合 `F`，其写入效果是
  `⋃_{n∈F} wr(n)`，即这些写入效果在格中的并。
- **单调性。** 如果对每个 `n` 都有 `wr(n) ⊆ D`，那么对每个
  `F ⊆ N` 都有 `⋃_{n∈F} wr(n) ⊆ D`（并运算保持上界 `D`）。

`D` 是 `L` 中与我们相关的那个元素：状态所能容纳的通道集合。

## 3. 小步操作语义

**配置**是 `⟨F, σ⟩`，其中 `F ⊆ N ∪ {⊥e}` 是活跃前沿，
`σ : D ↦ Val` 是状态（从声明的通道到值的全映射；
每个通道 `c` 各有一个 reducer `⊕c`）。执行从 `⟨route(⊥s), σ0⟩` 开始，
且 `dom(σ0) = D`。

运行节点 `n` 会产生一个写入列表 `⟦n⟧ = [(c1,v1), …, (ck,vk)]`，
即它在运行时*实际*写入的通道（不一定是它*声明*的那些）。
状态更新判断 `σ ⊢ W ⇒ σ'` 负责应用一个写入列表：

                                           c ∈ D
    (Apply-ok)   ────────────────────────────────────────────────
                 σ ⊢ (c,v)::W  ⇒  σ[c ↦ σ(c) ⊕c v] ⊢ W ⇒ σ'

                                          c ∉ D
    (Apply-fault) ───────────────────────────────────────
                  σ ⊢ (c,v)::W  ⇒  ⊥                       (throws)

    (Apply-done)  σ ⊢ []  ⇒  σ

`(Apply-fault)` 正是 `GraphState::write` / `apply_writes` 在 `c ∉ D` 时
抛出 "Write to unknown channel" 的情形。在这个模型里，`⊥` 表示出错的结果。
这是状态应用中*唯一*会出错的规则，也就是运行时的写入守卫。

配置上的超步关系：

                 σ ⊢ (⋃_{n∈F} ⟦n⟧) ⇒ σ'        F' = route(F, σ')
    (Step)       ──────────────────────────────────────────────────
                 ⟨F, σ⟩  →  ⟨F', σ'⟩

                 σ ⊢ (⋃_{n∈F} ⟦n⟧) ⇒ ⊥
    (Step-fault) ─────────────────────────────
                 ⟨F, σ⟩  →  ⊥

    (Halt)       ⟨{⊥e}, σ⟩  →  ·          (terminates)

`route(F, σ')` 根据实际走过的边/路由（以及任何 `goto`/`Send`）算出下一个前沿。
一次运行就是序列 `⟨F0,σ0⟩ → ⟨F1,σ1⟩ → …`，受 `max_steps` 限制；
到达 `{⊥e}` 就**终止**，到达 `⊥` 就**出错**，跑满 `max_steps` 步而二者都没发生，就**停滞**。

抽象语义还包含两种结构性的分发错误：

- **悬空路由。** 如果 `route` 必须沿某条边/路由到达名称 `m ∉ N ∪ {⊥e}`，分发就没有定义（悬空引用）。在模型中记作 `→ ⊥`。
- **空路由分发。** 如果条件节点 `n` 的路由表 `R(n) = ∅`，
  那么在这个模型里，路由表给不出任何分发目标。在模型中记作 `→ ⊥`。

## 4. 把闸门看作良构性判断

`GraphValidator::validate` 返回错误和警告。**错误**恰好就是拒绝条件；当且仅当没有错误时，闸门才通过。
我们把四类错误（E3、E4-write、E8、E10）当作 `⊢ G ok` 的前提：

    (E3)  ∀ (a,b) ∈ E.  a ∈ N ∪ {⊥s}  ∧  b ∈ N ∪ {⊥e}
          ∀ conditional n, label ℓ.  R(n)(ℓ) ∈ N ∪ {⊥e}
          ∀ barrier n, m ∈ wait_for(n).  m ∈ N
    (E4)  ∀ n ∈ N.  wr(n) ⊆ D                       -- declared writes are declared
    (E8)  ∀ barrier n, m ∈ wait_for(n).  ∃ static edge/route into n from m
    (E10) ∀ conditional n with a closed ConditionSpec of labels Λ.
              dom(R(n)) = Λ   (no dead keys, no uncovered labels)
          ∀ conditional n.  R(n) ≠ ∅

          ────────────────────────────────────────────────────────────
                                  ⊢ G ok

**警告**（E5 覆盖竞争、E6 死通道、E7 不可达、E9
未同步的扇入、E11 没有通往终点的路径、E4-read 读取未声明的通道）
有意*不*作为 `⊢ ok` 的前提：第 7 节说明它们都不会导致出错，
所以要求它们不出现，反而会拒绝安全的图（过度拒绝）。这是一项设计取舍，
目录里称之为“健全性优先于覆盖面”。

还有一点覆盖面方面的保留，如实照录：只有当**每一种**节点类型都声明了契约时，
效果这一族检查（E4/E5/E6）才会运行；只要有一种类型的契约未知，就会整体停用。
所以只有在下面的条件下，`(E4)` 才是 `⊢ G ok` 的前提：

    (Cov)  every node in N has a declared effect contract ρ(n).

没有 `(Cov)`，闸门根本看不到写入，也就不对写入的健全性作任何断言，
下面的定理同样如此。

## 5. 诚实性假设

闸门推理的是*声明的*效果 `wr(n)`；运行时执行的是*实际的*写入 `⟦n⟧`。
两者之间的桥梁是：

    (H)  ∀ n ∈ N.  channels(⟦n⟧) ⊆ wr(n)

也就是说，每个节点只写它声明过的通道。`(H)` 是关于节点实现的假设，
静态闸门无法验证它，因为节点的 `run` 是不透明的 C++。
`gate_fuzz` 的第 2 层给出了一个违反 `(H)` 的节点（声明 `{out}`，
却写了 `phantom`）；这种情况在 6.4 中处理。

## 6. 健全性

固定一个满足 `⊢ G ok` 和 `(Cov)` 的 `G`。用 `Reach(G)` 表示从
`⟨route(⊥s), σ0⟩` 出发可达的配置集合。

### 6.1 引理（域不变式）

*对每个 `⟨F, σ⟩ ∈ Reach(G)`，有 `dom(σ) = D`。*

**证明。** 按构造，`dom(σ0) = D`。`(Apply-ok)` 只更新满足 `c ∈ D`（即其前提）的
`σ[c ↦ …]`，所以保持定义域不变，既不增加键，也不删除键。
`(Apply-fault)` 得到的是 `⊥`，而不是一个状态。因此每个不出错的步骤都保持
`dom(σ) = D`。对运行长度做归纳，该不变式始终成立。∎

### 6.2 引理（写入始终在声明范围内）

*假设 `(H)`。对每个可达的 `⟨F, σ⟩` 和每个 `n ∈ F`，
有 `channels(⟦n⟧) ⊆ D`。*

**证明。** 由 `(H)` 得 `channels(⟦n⟧) ⊆ wr(n)`。由 `⊢ G ok` 的前提 `(E4)` 得
`wr(n) ⊆ D`（因为 `(Cov)` 成立，所以可以使用它）。由传递性得
`channels(⟦n⟧) ⊆ D`。再对 `n ∈ F` 取并，由单调性（第 2 节）得
`channels(⋃_{n∈F} ⟦n⟧) ⊆ D`。∎

### 6.3 定理（进展性 / 不出错）

*假设 `⊢ G ok`、`(Cov)` 和 `(H)`。没有任何可达配置会步进到 `⊥`。
每次运行要么终止（到达 `{⊥e}`），要么在 `max_steps` 处停滞；绝不会出错。*

**证明。** 步进到 `⊥` 只可能经由 `(Step-fault)`、悬空路由或空路由分发。
我们逐一排除。

- **写入出错 `(Step-fault)`。** 这要求 `σ ⊢ (⋃_{n∈F} ⟦n⟧) ⇒ ⊥`，即
  合并后的写入列表里存在某个 `(c,v)` 满足 `c ∉ D`。由引理 6.2，
  `channels(⋃_{n∈F} ⟦n⟧) ⊆ D`，所以不存在这样的 `c`。`(Apply-fault)` 永远不会启用；
  每次应用都经 `(Apply-ok)`/`(Apply-done)` 归约到某个状态
  `σ'`（由引理 6.1，`dom(σ') = D`）。矛盾。

- **悬空路由。** `route` 会沿边 `(a,b) ∈ E`、路由目标
  `R(n)(ℓ)` 或屏障成员走。前提 `(E3)` 给出 `b ∈ N ∪ {⊥e}`、
  `R(n)(ℓ) ∈ N ∪ {⊥e}`，以及每个屏障成员 `∈ N`。所以每个被沿用的目标
  都指向一个存在的节点或 `⊥e`；分发有定义。

- **空路由分发。** 这要求到达某个 `R(n) = ∅` 的条件节点 `n`。
  前提 `(E10)` 保证每个条件节点都有 `R(n) ≠ ∅`。已排除。

在任何可达配置上，都不存在通往 `⊥` 的可用规则。除此之外，步进关系是全的
（一个超步总会产生下一个前沿），所以每次运行都是一条由不出错的步骤组成的、
无限或终止的链，并在 `max_steps` 处截断。因此它要么终止，要么停滞，绝不会出错。∎

`(E8)` 检查的是屏障成员已声明的静态入边/路由。它并不证明所有成员都会执行：
互斥的路由可能让 AND-join 永远无法触发。这个证明不能确立屏障的活性，
也不能把每一种死锁与有意设计的环区分开。在抽象模型里“不出错”，
并不要求保证终止。

### 6.4 推论（相对于诚实契约，闸门是健全的）

*如果闸门通过（`⊢ G ok`），契约覆盖完整（`(Cov)`），并且所有契约都诚实（`(H)`），
那么执行不会出错：不会写入未声明的通道，也不会出现悬空路由或空路由的分发错误。*

模型中的蕴含式是 `gate-pass ⟹ no-modeled-fault`；它的逆否命题是
`modeled-fault ⟹ gate-reject`，而不是 `gate-reject ⟹ fault`。历史语料库检查了
若干具体的被拒绝样例，但不能证明每一个被拒绝的图都一定会出错。保留下来的 fuzz 结果
显示，在 2000 个变异体中，通过闸门之后没有出错。

### 6.5 命题（`(H)` 是必要的；运行时是兜底）

*没有 `(H)` 时，`⊢ G ok` 并不蕴含不出错，但整个组合系统（闸门 + 运行时守卫）
仍然是 fail-stop：它不会进入未定义行为，只会干净地到达 `⊥`。*

**证明。** *必要性。* 取 `G` 为一个一致的种子图，再加一个节点 `n`，
其 `ρ(n) = ({}, {out})`，`out ∈ D`，但 `⟦n⟧ = [(phantom, 1)]`，`phantom ∉ D`。
`⊢ G ok` 的每个前提都成立（尤其是 `(E4)`：`wr(n) = {out} ⊆ D`），
所以闸门通过。然而运行 `n` 会对 `phantom` 触发 `(Apply-fault)`，
运行因此出错。故当 `(H)` 不成立时，`⊢ G ok ⇏ non-fault`。（这正是
`gate_fuzz` 第 2 层的说谎节点，500/500。）

*Fail-stop。* 这个违规会被 `(Apply-fault)` 本身捕获：这是一次有定义的、
确定性的 `throw`，而不是未定义行为。因此即使没有 `(H)`，执行也不会破坏状态，
不会跑进 UB：它会带着诊断信息停下来。对于静态闸门不得不假设的这一条前提，
运行时的写入守卫就是健全的兜底。∎

两者合起来，给出了*无条件*的安全性陈述；对整个系统而言，这才是诚实的说法：

> **相对于诚实的效果契约，静态闸门是健全的（定理 6.3 /
> 推论 6.4）。即使契约说谎，运行时写入守卫也让执行保持 fail-stop
> （命题 6.5）。在所述假设下，在这台抽象机内，从 `⊢ G ok` 出发可达的
> 任何配置都不会出现未定义行为。**

## 7. 为什么警告不是前提

为完整起见（针对“不过度拒绝”），下面逐类说明每种警告对进展性都无害，
这也正是它们被排除在 `⊢ G ok` 之外的理由：

- **E7（节点不可达）、E11（没有通往 `__end__` 的路径）。** 不可达的节点
  永远不会出现在任何可达的前沿 `F` 中，所以它既不产生写入，也不参与路由，
  因此不会出错（定理 6.3 只对 `n ∈ F` 量化）。E11 关乎终止，而不是出错。
- **E9（未同步的扇入）、E5（覆盖竞争）。** 它们会让通道里的*值*取决于
  超步中各分支到达的先后顺序（非确定性），但每次写入仍然指向某个 `c ∈ D`
  （引理 6.2 不受影响），所以不会出错。reducer
  `⊕c` 是全函数。依赖顺序是语义上的隐患，而不是卡死的状态。
- **E6（死通道）。** 声明了却从未写入的通道保持初始值；
  读取它会得到定义域内的值。不会出错。
- **E4-read（读取未声明的通道）。** 在模型里，其结果为 `null`
  （代码返回空值，读取时不抛异常）。不会出错，所以是警告，
  而不是像 E4-write 那样的错误。

每一项都是真实的语义性质，但没有一项能驱动 `→ ⊥`；禁止它们会拒绝安全的 harness，
所以闸门把它们保留为警告。这就是目录中“健全性优先于覆盖面”的形式化含义。

## 8. 范围与诚实的局限

- **不涉及终止性。** 这里的健全性指的是*不出错*，而不是*会终止*。环是合法的
  （通过 `goto`/`Send` 形成循环），会一直跑到 `max_steps`，然后停滞。
  定理说的是：通过闸门的图绝不会*抛出异常*，也不会碰到 *UB*，而不是说它一定会停机。
  `gate_fuzz` 把停滞也视为不出错，正是出于这个原因。
- **抽象的保真度。** 证明针对的是第 3 节的模型，该模型照着代码建立，
  但并非从代码中提取。经验性的测试工具负责检验保真度；如果它们与定理出现分歧，
  就说明模型（或代码）已经偏离了，`gate_fuzz` 第 1 层就是一直在跑的回归防线。
- **覆盖 `(Cov)`。** 只有当每种节点类型都声明了契约时，才宣称写入的健全性（E4），
  这与“只要有一种类型未知，整个效果检查族就停用”的闸门行为一致。
  覆盖不完整时，闸门沉默，定理也同样沉默。
- **诚实 `(H)`。** 它是假设，是必要的（命题 6.5），并且有运行时兜底。
  要对某个具体节点机械地证明 `(H)`，就得验证它的 `run` 函数体，这超出了本文的范围；
  写入守卫是务实的替代办法。
- **仅限静态路由。** 前提 `(E3)` 约束的是*静态*的边/路由/屏障结构，
  因此定理 6.3 中的悬空路由情形，只覆盖闸门看得到的目标。
  `Command.goto`/`Send` 的目标是作为*运行时的值*算出来的
  （这正是 E7 可达性只是警告而不是错误的原因）。这类动态目标不在静态闸门的视野之内，
  与写入方面的 `(H)` 是同一类缺口，属于调度器在运行时要处理的问题，
  不是本定理的断言。证明的范围限于静态路由的分发；动态路由同样要靠运行时检查。

## 9. 与经验性测试工具的关系

| 制品 | 与这套理论的关系 |
|---|---|
| [`the_beast_gate_eval.cpp`](the_beast_gate_eval.cpp) | 在带标签的语料库上检验推论 6.4（4/4）：每个满足 `⊢ G ok` 的图都能干净地运行，每个带错误的图都会出错。 |
