# Coherence Gate의 건전성 — 형식 증명 문서

**Languages:** [English](SOUNDNESS.md) | [한국어](SOUNDNESS.ko.md) | [日本語](SOUNDNESS.ja.md) | [简体中文](SOUNDNESS.zh-CN.md)

## 타입 기반 provider 전환 — 증거의 범위

typed API로 옮긴 C++ 작성/수정 경로는 타입이 있는 `ProviderRequest`와 `sp::Message` 기록을 만들고, 반환된 모든 네이티브 메시지/파트를 포함한 불변 `sp::Outcome` 전체를 소비합니다. 텍스트 추출은 후보 JSON/Python을 파싱할 때만 쓰며, 네이티브 대화 기록을 대체하는 데는 쓰지 않습니다. 컴파일러/파싱/초기화 피드백은 이 메시지들 뒤에 덧붙입니다. 의미 수정(semantic repair)은 프로그램마다 정해진 시도 횟수로 제한됩니다(실제 작성: 3회, Forge 서버 생성: 2회). 전송 재시도도 아니고 무제한 진화도 아닙니다.

[Forge 소스 계약](README.md)은 `MaxTokens`로 끊겨 출력이 비었을 때의 복구를 별도로 제한합니다.
상한을 두 배로 올린 호출 한 번만 허용하고, 데드라인은 300초로 고정하며, 결과와 사용량을 보존합니다.
실패나 observer/정산(settlement) 오류는 재시도하지 않습니다.

비공개 OpenRouter 경로 `~deepseek/deepseek-v4-flash-latest`와 `zdr: true`(공유 예제 provider factory)를 그대로 유지합니다. 조건에 맞는 무보존(zero-data-retention) 엔드포인트가 없으면 데이터를 보존하는 provider에 내용을 보내지 않고 실패합니다. ZDR 엔드포인트 목록은 데이터 거주지(residency) 보장도 아니고 현재 사용 가능하다는 증명도 아닙니다. 실제 실행에는 승인된 키, 네트워크/provider 가용성, 유료 사용 한도가 필요하며, 프롬프트, 내보낸 스키마, 진단 결과, 네이티브 기록이 이 경로로 전송됩니다. 생성된 Python 서버를 실행하는 일에는 로컬 코드 실행에 따른 별도의 신뢰 경계가 있으며, 이는 NeoGraph의 Python provider 바인딩과는 별개입니다. 키와 비공개 프롬프트는 절대 공개해서는 안 됩니다. null일 수 있는 토큰 카운터는 달러 비용이 아닙니다. 가격과 실제 청구 대상 사용량은 별도로 확인해야 하는 선행 조건입니다.

보존된 interface 3의 범위 한정 런타임 증거는 오프라인에서 실제로 수행한 strict Core 컴파일, 진화, 체크포인트 롤백을 다룹니다. 모든 live/apex/forge/script 변형이나 벤더 추론을 검증한 것은 아닙니다. 아래에 남아 있는 콘솔 기록, 벤치마크/퍼즈 결과, 실제 실행 주장은 과거의 기록이며 interface 4에서 측정한 값이 아닙니다. Coherence gate가 보증하는 것은 명시된 구조/효과 계약 속성이며, provider 전송이나 프라이버시의 정확성, 모델이 낸 내용의 의미상 진실은 보증하지 않습니다. Python provider 바인딩은 이제 typed API를 따르지만, 그 검증은 이 C++ 실행과는 별개입니다.

이 문서는 cookbook의 실험용 하니스가 바탕으로 하는 이론입니다.
`gate_eval`은 레이블이 붙은 코퍼스에서 coherence gate가 건전함을 *측정*했고,
`gate_fuzz`는 수천 개의 변이(mutant)에 대해 그 경계를 *측정*해 정리했습니다(정직한 효과 계약에서는 건전하고, 정직하지 않은 계약은 런타임 안전망이 잡아 줍니다).
이 문서는 하니스 실행의 스몰스텝 연산 의미론과, 게이트가 다루는 효과 격자 위에서 이에 대응하는 정리를 *증명*합니다.

이 증명은 아래의 추상 기계를 대상으로 합니다. 이 기계에서는 리듀서가 모든 입력에 대해 정의되고, 노드 본문은 항상 값을 반환하며, 선언된 채널이 고정되어 있고, 디스패치도 모든 경우에 정의되며 정적으로 라우팅됩니다. 노드나 리듀서의 예외, 취소, provider/도구 실패, 리소스 한도, 체크포인트/보관(custody) 오류, 임의로 생성된 코드는 대상이 아닙니다. 실제 C++ 엔진에는 이런 실패 유형이 더 있습니다. 인용한 구현 파일은 이 모델을 세우는 근거일 뿐이며, 과거의 코퍼스가 C++ 구현을 기계적으로 검증하는 것은 아니고, 이 모델 밖에서 정의되지 않은 동작(undefined behavior)이 없음을 보이는 것도 아닙니다.

표기법은 ASCII입니다. `⊆ ∪ ∩ ∅`는 집합 연산,
`⟨…⟩`는 기계 구성(configuration), `↦`는 맵의 항목, `→`는 단계 관계(step relation),
`⊢ G ok`는 정형성(well-formedness) 판정입니다.

## 1. 구문

하니스(컴파일된 그래프)는 다음과 같습니다.

    G = (N, E, D, ρ, R)

- `N`      — 노드 이름의 유한 집합입니다. 특별한 이름 두 개 `⊥s = __start__`와
             `⊥e = __end__`는 `N`에 속하지 않습니다.
- `E ⊆ (N ∪ {⊥s}) × (N ∪ {⊥e})` — 정적 엣지입니다.
- `D`      — **선언된 채널**(`channels` 블록)의 유한 집합입니다.
- `ρ : N → 𝒫(Chan) × 𝒫(Chan)` — 각 노드의 **효과 계약**입니다.
             `ρ(n) = (rd(n), wr(n))`로 쓰며, 노드가 읽겠다고 선언한 채널과
             쓰겠다고 선언한 채널입니다. `Chan`은 채널 이름 전체의 집합이고, `D ⊆ Chan`입니다.
- `R`      — 조건 노드의 라우팅 데이터입니다. 조건 노드 `n`에 대해
             `R(n)`은 레이블에서 대상으로 가는 부분 함수(라우트 맵)이며,
             레이블 집합을 고정하는 `ConditionSpec`을 선언할 수도 있습니다.

Barrier(AND-join 노드)는 `wait_for ⊆ N` 집합을 가집니다. 필요한 경우 이 집합을 `G`에 포함해서 다룹니다.

## 2. 효과 격자

효과는 채널의 멱집합으로 만든 격자 위에 놓입니다.

    L = (𝒫(Chan), ⊆, ∪, ∩, ∅, Chan)

join은 `∪`, meet은 `∩`, 최하원(bottom)은 `∅`, 최상원(top)은 `Chan`입니다. 여기서 쓰는 사실은 두 가지입니다.

- **합성은 join입니다.** 노드 집합 `F`를 한 슈퍼스텝에서 실행할 때의 쓰기 효과는
  `⋃_{n∈F} wr(n)`이며, 각 노드의 쓰기 효과를 격자 join으로 합친 것입니다.
- **단조성.** 모든 `n`에 대해 `wr(n) ⊆ D`이면 모든 `F ⊆ N`에 대해 `⋃_{n∈F} wr(n) ⊆ D`입니다
  (join은 상계 `D`를 보존합니다).

`L`에서 의미가 있는 원소는 `D`입니다. 상태가 가질 수 있는 채널의 집합입니다.

## 3. 스몰스텝 연산 의미론

**구성(configuration)**은 `⟨F, σ⟩`입니다. `F ⊆ N ∪ {⊥e}`는 활성 frontier이고,
`σ : D ↦ Val`은 상태입니다(선언된 채널에서 값으로 가는 전함수이며, 각 채널 `c`에는 리듀서 `⊕c`가 있습니다). 실행은
`dom(σ0) = D`인 `⟨route(⊥s), σ0⟩`에서 시작합니다.

노드 `n`을 실행하면 쓰기 목록 `⟦n⟧ = [(c1,v1), …, (ck,vk)]`가 나옵니다. 이는 노드가 런타임에 *실제로* 쓰는
채널이며, 노드가 *선언한* 채널과 같을 필요는 없습니다.
상태 갱신 판정 `σ ⊢ W ⇒ σ'`은 쓰기 목록을 적용합니다.

                                           c ∈ D
    (Apply-ok)   ────────────────────────────────────────────────
                 σ ⊢ (c,v)::W  ⇒  σ[c ↦ σ(c) ⊕c v] ⊢ W ⇒ σ'

                                          c ∉ D
    (Apply-fault) ───────────────────────────────────────
                  σ ⊢ (c,v)::W  ⇒  ⊥                       (throws)

    (Apply-done)  σ ⊢ []  ⇒  σ

`(Apply-fault)`는 `c ∉ D`일 때 `GraphState::write` / `apply_writes`가
"Write to unknown channel"을 던지는 동작과 정확히 같습니다. 이 모델에서 `⊥`는
fault로 끝난 결과입니다. 상태를 적용하는 과정에서 fault가 날 수 있는 규칙은 이 하나뿐이며,
이 규칙이 런타임 쓰기 가드(write-guard) 역할을 합니다.

구성 위의 슈퍼스텝 관계는 다음과 같습니다.

                 σ ⊢ (⋃_{n∈F} ⟦n⟧) ⇒ σ'        F' = route(F, σ')
    (Step)       ──────────────────────────────────────────────────
                 ⟨F, σ⟩  →  ⟨F', σ'⟩

                 σ ⊢ (⋃_{n∈F} ⟦n⟧) ⇒ ⊥
    (Step-fault) ─────────────────────────────
                 ⟨F, σ⟩  →  ⊥

    (Halt)       ⟨{⊥e}, σ⟩  →  ·          (terminates)

`route(F, σ')`는 선택된 엣지/라우트(와 `goto`/`Send`)로부터 다음 frontier를
계산합니다. 실행(run)은 `max_steps`로 제한되는 `⟨F0,σ0⟩ → ⟨F1,σ1⟩ → …` 수열입니다.
`{⊥e}`에 도달하면 **종료**하고, `⊥`에 도달하면 **fault**가 나며,
둘 다 아닌 채로 `max_steps` 스텝을 실행하면 **stall**(멈춤)이 됩니다.

추상 의미론에는 구조적인 디스패치 fault도 두 가지 있습니다.

- **끊어진 라우트(dangling route).** `route`가 엣지/라우트를 따라 `m ∉ N ∪ {⊥e}`인 이름으로 가야 하면
  디스패치가 정의되지 않습니다(끊어진 참조). 이를 `→ ⊥`로 모델링합니다.
- **빈 라우트 디스패치(empty-route dispatch).** 조건 노드 `n`의 라우트 맵이 `R(n) = ∅`이면,
  이 모델에서는 맵이 디스패치 대상을 하나도 제공하지 못합니다.
  이를 `→ ⊥`로 모델링합니다.

## 4. 정형성 판정으로 본 게이트

`GraphValidator::validate`는 오류(error)와 경고(warning)를 반환합니다. **오류**는 정확히 거부 조건이며,
게이트는 오류가 하나도 없을 때에만 통과합니다. 네 오류 계열(E3, E4-write, E8, E10)을
`⊢ G ok`의 전제로 읽습니다.

    (E3)  ∀ (a,b) ∈ E.  a ∈ N ∪ {⊥s}  ∧  b ∈ N ∪ {⊥e}
          ∀ conditional n, label ℓ.  R(n)(ℓ) ∈ N ∪ {⊥e}
          ∀ barrier n, m ∈ wait_for(n).  m ∈ N
    (E4)  ∀ n ∈ N.  wr(n) ⊆ D                       -- declared writes are declared
    (E8)  ∀ barrier n, m ∈ wait_for(n).  ∃ static edge/route into n from m
    (E10) ∀ conditional n with a closed ConditionSpec of labels Λ.
              dom(R(n)) = Λ   (no dead keys, no uncovered labels)
          ∀ conditional n.  R(n) ≠ ∅

          ────────────────────────────────────────────────────────────
                                  ⊢ G ok

**경고**(E5 overwrite 경합, E6 죽은 채널, E7 도달 불가, E9
동기화되지 않은 fan-in, E11 종료 노드로 가는 경로 없음, 선언되지 않은 채널을 읽는 E4-read)는
일부러 `⊢ ok`의 전제에 *넣지 않았습니다*. §7에서 보이듯 이들은 모두 fault를 일으킬 수 없으므로,
경고가 없을 것을 요구하면 안전한 그래프까지 거부하게 됩니다(과잉 거부). 카탈로그가 "커버리지보다 건전성"이라고 밝힌 설계 선택입니다.

커버리지에 관한 주의점이 하나 있으며, 이를 그대로 반영합니다. 효과 계열(E4/E5/E6)은 **모든** 노드 타입이
계약을 선언했을 때에만 실행되고, 계약을 알 수 없는 타입이 하나라도 있으면 꺼집니다.
따라서 `(E4)`가 `⊢ G ok`의 전제가 되는 것은 다음 조건 아래에서뿐입니다.

    (Cov)  every node in N has a declared effect contract ρ(n).

`(Cov)`가 없으면 게이트는 쓰기를 전혀 볼 수 없으므로 쓰기에 관한 건전성을 주장하지 않으며, 아래 정리도 마찬가지입니다.

## 5. 정직성 가설

게이트는 *선언된* 효과 `wr(n)`을 근거로 추론하고, 런타임은 *실제* 쓰기 `⟦n⟧`을 실행합니다. 둘을 잇는 가설은 다음과 같습니다.

    (H)  ∀ n ∈ N.  channels(⟦n⟧) ⊆ wr(n)

즉, 모든 노드는 자신이 선언한 채널에만 씁니다. `(H)`는 노드 구현에 관한 가정이지 정적 게이트가
검증할 수 있는 것이 아닙니다. 노드의 `run`은 내부를 알 수 없는 C++이기 때문입니다. `gate_fuzz`의 Layer 2는 `(H)`를 어기는
노드(`{out}`을 선언하고 `phantom`에 씀)를 보여 주며, 그 경우는 §6.4에서 다룹니다.

## 6. 건전성

`⊢ G ok`와 `(Cov)`를 만족하는 `G`를 하나 고정합니다. `⟨route(⊥s), σ0⟩`에서 도달할 수 있는 구성의 집합을
`Reach(G)`로 씁니다.

### 6.1 보조정리 (정의역 불변식)

*모든 `⟨F, σ⟩ ∈ Reach(G)`에 대해 `dom(σ) = D`입니다.*

**증명.** 정의상 `dom(σ0) = D`입니다. `(Apply-ok)`는 `c ∈ D`인 경우(전제)에만 `σ[c ↦ …]`로 갱신하므로
정의역을 보존하며, 키를 추가하거나 제거하지 않습니다. `(Apply-fault)`는 상태가 아니라 `⊥`를 냅니다. 따라서
fault가 아닌 모든 스텝은 `dom(σ) = D`를 보존합니다. 실행 길이에 따른 귀납법으로 이 불변식은 처음부터 끝까지 유지됩니다. ∎

### 6.2 보조정리 (선언된 범위에 머무는 쓰기)

*`(H)`를 가정합니다. 도달 가능한 모든 `⟨F, σ⟩`와 모든 `n ∈ F`에 대해
`channels(⟦n⟧) ⊆ D`입니다.*

**증명.** `(H)`에서 `channels(⟦n⟧) ⊆ wr(n)`입니다. `⊢ G ok`의 전제 `(E4)`에서 `wr(n) ⊆ D`입니다
(`(Cov)`가 성립하므로 쓸 수 있습니다). 추이성으로
`channels(⟦n⟧) ⊆ D`를 얻습니다. `n ∈ F`에 대해 join을 취하면 단조성(§2)으로
`channels(⋃_{n∈F} ⟦n⟧) ⊆ D`입니다. ∎

### 6.3 정리 (진행 / fault 없음)

*`⊢ G ok`, `(Cov)`, `(H)`를 가정합니다. 도달 가능한 어떤 구성도 `⊥`로 진행하지 않습니다.
모든 실행은 종료하거나(`{⊥e}`에 도달) `max_steps`에서 stall하며, fault가 나는 일은 없습니다.*

**증명.** 스텝이 `⊥`에 도달하는 경로는 `(Step-fault)`, 끊어진 라우트, 빈 라우트 디스패치뿐입니다.
이 셋을 하나씩 배제합니다.

- **쓰기 fault `(Step-fault)`.** 이 fault가 일어나려면 `σ ⊢ (⋃_{n∈F} ⟦n⟧) ⇒ ⊥`여야 하며, 즉
  합쳐진 쓰기 목록에 `c ∉ D`인 `(c,v)`가 있어야 합니다. 보조정리 6.2에서
  `channels(⋃_{n∈F} ⟦n⟧) ⊆ D`이므로 그런 `c`는 없습니다. `(Apply-fault)`는 적용될 수 없고,
  모든 적용은 `(Apply-ok)`/`(Apply-done)`으로 줄어들어 상태
  `σ'`가 됩니다(보조정리 6.1에서 `dom(σ') = D`). 따라서 모순입니다.

- **끊어진 라우트.** `route`가 따라가는 것은 엣지 `(a,b) ∈ E`, 라우트 대상
  `R(n)(ℓ)`, barrier 멤버입니다. 전제 `(E3)`에서 `b ∈ N ∪ {⊥e}`,
  `R(n)(ℓ) ∈ N ∪ {⊥e}`가 나오고, 모든 barrier 멤버는 `∈ N`입니다. 따라서 따라가는 대상은
  모두 존재하는 노드이거나 `⊥e`이며, 디스패치는 정의됩니다.

- **빈 라우트 디스패치.** `R(n) = ∅`인 조건 노드 `n`에 도달해야 일어납니다.
  전제 `(E10)`에서 모든 조건 노드에 대해 `R(n) ≠ ∅`이므로 배제됩니다.

도달 가능한 어떤 구성에서도 `⊥`로 가는 규칙은 적용되지 않습니다. 그 밖의 스텝 관계는 전함수이므로
(슈퍼스텝은 항상 다음 frontier를 만듭니다) 모든 실행은 fault 없는 스텝의 열이며,
그 열은 무한히 이어지거나 종료하고, `max_steps`에서 잘립니다.
따라서 실행은 종료하거나 stall할 뿐 fault가 나지 않습니다. ∎

`(E8)`은 barrier 멤버에 대해 선언된 정적 진입 엣지/라우트가 있는지를 검사합니다. 모든 멤버가
실행된다는 것을 증명하지는 않습니다. 서로 배타적인 라우트 때문에 AND-join이 발동하지 못할 수 있습니다. 이 증명은
barrier의 liveness를 보이지 않으며, 모든 교착(deadlock)과 의도된 순환을 구분하지도 않습니다.
추상 모델에서 fault가 없다는 것은 종료 보장을 요구하지 않습니다.

### 6.4 따름정리 (정직한 계약을 전제로 한 게이트의 건전성)

*계약이 전부 선언되어 있고 `(Cov)`, 모든 계약이 정직할 때 `(H)`, 게이트를 통과하면(`⊢ G ok`)
실행에서 fault가 나지 않습니다. 선언되지 않은 채널에 쓰는 일도,
끊어진 라우트나 빈 라우트 디스패치 fault도 없습니다.*

모델이 말하는 함의는 `gate-pass ⟹ no-modeled-fault`이고, 그 대우는
`modeled-fault ⟹ gate-reject`이지 `gate-reject ⟹ fault`가 아닙니다. 과거의 코퍼스는
거부된 특정 예제를 확인할 뿐, 거부된 모든 경우가 fault를 낸다는 것을 증명하지는 않습니다.
남아 있는 퍼즈 결과에는 변이 2000개 가운데 게이트를 통과한 뒤 fault가 난 경우가 없다고 보고되어 있습니다.

### 6.5 명제 (`(H)`의 필요성과 안전망으로서의 런타임)

*`(H)`가 없으면 `⊢ G ok`가 fault 없음을 함의하지 않습니다. 그러나 게이트와 런타임 가드를 합친 시스템은
여전히 fail-stop입니다. 정의되지 않은 동작에 이르지 않고, 깔끔한 `⊥`에서만 멈춥니다.*

**증명.** *필요성.* `G`를 정합적인(coherent) 시드에 노드 `n`을 더한 것으로 잡습니다.
`ρ(n) = ({}, {out})`이고 `out ∈ D`이지만 `⟦n⟧ = [(phantom, 1)]`, `phantom ∉ D`입니다.
`⊢ G ok`의 모든 전제가 성립하므로(특히 `(E4)`: `wr(n) = {out} ⊆ D`) 게이트는 통과합니다.
그런데도 `n`을 실행하면 `phantom`에서 `(Apply-fault)`가 발동하므로 실행은 fault가 납니다. 따라서
`(H)`가 깨지면 `⊢ G ok ⇏ non-fault`입니다. (`gate_fuzz` Layer 2의 거짓말하는 노드가 바로 이 경우이며 500/500입니다.)

*Fail-stop.* 위반은 `(Apply-fault)` 자체가 잡아냅니다. 이는 정의된 결정적 `throw`이지
정의되지 않은 동작이 아닙니다. 그러므로 `(H)`가 없어도 실행이 상태를 망가뜨리거나 UB로 빠져나가는 일은 없고,
진단 메시지와 함께 멈춥니다. 런타임 쓰기 가드는 정적 게이트가 가정해야 하는 유일한 가설을 받쳐 주는
건전한 안전망입니다. ∎

이 둘을 합치면 시스템 전체에 대해 할 수 있는 정직한 진술, 즉 *무조건적인* 안전성 진술이 됩니다.

> **정적 게이트는 정직한 효과 계약을 전제로 건전합니다(정리 6.3 /
> 따름정리 6.4). 계약이 거짓이더라도 런타임 쓰기 가드가 실행을 fail-stop으로 만듭니다(명제 6.5).
> 이 추상 기계에서 명시한 가정 아래에서는, `⊢ G ok`로 도달할 수 있는 어떤 구성도 정의되지 않은 동작을 보이지 않습니다.**

## 7. 경고를 전제로 삼지 않는 이유

완전성을 위해("과잉 거부 없음"의 의미에서) 경고 종류마다 진행(progress)에 해가 없음을 보이며,
이 점이 `⊢ G ok`에서 경고를 제외하는 근거입니다.

- **E7(도달 불가 노드), E11(`__end__`로 가는 경로 없음).** 도달할 수 없는 노드는 어떤 도달 가능한 frontier `F`에도
  들어가지 않으므로 쓰기도 라우팅도 만들지 못하고, 따라서 fault를 낼 수 없습니다(정리 6.3은 `n ∈ F`만 대상으로 합니다).
  E11은 fault가 아니라 종료에 관한 문제입니다.
- **E9(동기화되지 않은 fan-in), E5(overwrite 경합).** 이 경우 채널에 들어가는 *값*이
  슈퍼스텝에 도착하는 순서에 따라 달라지지만(비결정성), 모든 쓰기는 여전히 `c ∈ D`를 대상으로 하므로(보조정리 6.2는 영향을 받지 않음)
  fault는 없습니다. 리듀서
  `⊕c`는 전함수입니다. 순서 의존성은 의미상의 위험이지 멈춘 상태가 아닙니다.
- **E6(죽은 채널).** 선언만 되고 쓰이지 않은 채널은 초기값을 유지하며, 그 채널을 읽으면
  정의역 안의 값이 나옵니다. fault는 없습니다.
- **E4-read(선언되지 않은 채널 읽기).** `null`을 내는 것으로 모델링합니다(코드는 읽을 때 예외를 던지지 않고
  null 값을 반환합니다). fault가 없으므로 E4-write와 달리 오류가 아니라 경고입니다.

이들은 모두 실제로 의미 있는 속성이지만 어느 것도 `→ ⊥`를 일으키지 않습니다. 이를 금지하면 안전한 하니스까지
거부하게 되므로 게이트는 경고로만 둡니다. 카탈로그가 말하는 "커버리지보다 건전성"의 형식적 내용이 바로 이 점입니다.

## 8. 범위와 정직한 한계

- **종료는 보장하지 않습니다.** 여기서 건전성은 *fault 없음*이지 *종료*가 아닙니다. 순환은 정당하며
  (`goto`/`Send`로 만드는 반복) `max_steps`까지 실행되어 stall이 됩니다. 정리가 말하는 것은 게이트를 통과한 그래프가
  *예외를 던지거나* *UB*에 빠지지 않는다는 것이지, 반드시 멈춘다는 것이 아닙니다. 바로 이 때문에 `gate_fuzz`는 stall을 fault로 보지 않습니다.
- **추상화의 충실도.** 증명은 §3의 모델 위에서 이루어집니다. 이 모델은 코드를 본떴지만 코드에서 추출한 것은 아닙니다.
  실험용 하니스가 충실도를 확인하는 수단입니다. 하니스와 정리가 어긋난다면 모델(또는 코드)이 달라졌다는 뜻이며,
  `gate_fuzz` Layer 1이 항상 켜 두는 회귀 방지 장치입니다.
- **커버리지 `(Cov)`.** 쓰기 건전성(E4)은 모든 노드 타입이 계약을 선언한 경우에만 주장합니다.
  "알 수 없는 타입이 하나라도 있으면 그 계열을 끈다"는 게이트의 동작을 그대로 반영한 것입니다.
  커버리지가 부분적이면 게이트는 아무 말도 하지 않고, 정리도 마찬가지입니다.
- **정직성 `(H)`.** 가정이고, 꼭 필요하며(명제 6.5), 런타임이 안전망으로 받쳐 줍니다. 특정 노드의 `(H)`를
  기계로 증명하려면 그 노드의 `run` 본문을 검증해야 하는데, 이는 이 문서의 범위 밖입니다. 쓰기 가드가 현실적인 대안입니다.
- **정적 라우팅만 다룹니다.** 전제 `(E3)`은 *정적* 엣지/라우트/barrier 구조를 제약하므로, 정리 6.3의 끊어진 라우트 경우는
  게이트가 볼 수 있는 대상만 포함합니다. `Command.goto`/`Send`는 대상을 *런타임 값*으로 계산합니다
  (E7 도달 가능성이 오류가 아니라 경고인 이유가 바로 이 때문입니다). 이런 동적 대상은 정적 게이트의 시야 밖에 있으며,
  쓰기에 관한 `(H)`와 같은 모양의 틈입니다. 이는 스케줄러가 런타임에 처리할 문제이고 이 정리가 주장하는 바가 아닙니다.
  증명의 범위는 정적으로 라우팅되는 디스패치이며, 동적 라우팅도 마찬가지로 런타임에 검사됩니다.
