## 보충: 데이터베이스 API 프로파일

기준선 측정 뒤에 추가로 72번을 실행해 프로파일링 켬/끔, 호출 1번 대 21번, 3회 반복, 두 제어 모드, 모든 백엔드를 비교했습니다. 표의 값은 `(21-run process total − 1-run process total) / 20`으로 구한 뒤 반복 간 중앙값을 취한 것입니다. 호출 횟수의 차이는 세 번의 반복에서 모두 같았습니다. 시간의 차이는 콜드 프로세스의 편차가 섞인 추정치로 남습니다.

| 경로 | run당 SQLite step 호출 | run당 SQLite exec 호출 | run당 SQLite 커밋 | run당 동기 libpq 호출 |
| --- | --- | --- | --- | --- |
| memory-cpp | 0 | 0 | 0 | 0 |
| memory-javascript | 0 | 0 | 0 | 0 |
| sqlite-cpp | 73 | 14 | 7 | 0 |
| sqlite-javascript | 117 | 18 | 9 | 0 |
| postgres-cpp | 0 | 0 | 0 | 64 |
| postgres-javascript | 0 | 0 | 0 | 108 |

SQLite step은 행마다 반복될 수 있으므로 서로 다른 SQL 문의 수가 아닙니다. `exec`에는 트랜잭션 제어가 들어 있고 중첩된 step은 제외합니다. libpq의 횟수와 시간은 동기 방식의 `PQexec`/`PQexecParams`만 다루며, 비동기 체크포인트 경로와 연결 수립은 제외합니다. 클라이언트 CPU에는 PostgreSQL 서버가 포함되지 않습니다. API의 벽시계 구간과 클라이언트 CPU는 서로 겹치므로 더하거나 기준선 지연 시간의 완전한 분할로 취급해서는 안 됩니다.

memory 대조군에서는 데이터베이스 호출이 기록되지 않았습니다. JS SQLite 케이스에서는 호출 한 번당 커밋 9번과 외부 step 호출 117번이 일어납니다. 시간을 잰 이 데이터베이스 호출 밖의 CPU 작업도 프로파일링해 볼 가치가 있습니다. JS PostgreSQL 케이스에서는 호출 한 번당 동기 호출이 108번 발생하므로, JIT 실험에 앞서 왕복 횟수를 줄이는 것이 구체적인 목표가 됩니다.

보충 증거는 `artifacts/program-costs-20260907/profile/`에 있습니다. 처음 만든 프로파일러는 SQLite `exec`의 트랜잭션 호출을 빠뜨렸으므로 그 예비 출력은 사용하지 않았습니다. 파일 복사가 끝난 뒤 수정한 프로파일을 다시 실행했습니다. 그런데 그 뒤에 한 프로파일링 실행과 프로파일링하지 **않은** 실행이 모두, memory 대조군을 포함해 주 기준선보다 눈에 띄게 느렸습니다. 이 환경 변동의 원인은 따로 밝혀내지 못했습니다. 그래서 이 문서에서는 안정적인 호출 횟수만 인정하고, 원시 API 시간과 CPU 시간은 보관하되 **주 기준선의 지연 시간을 설명하는 근거로 쓰지 않습니다.** 주 기준선 데이터는 이 복사 문제가 생기기 전에 얻은 것이며 7회 반복 전체와 그 산포를 유지합니다.

기존 `bench_program`도 새 프로세스 세 개에서 C++ Program 경로가 2.21–2.31 ms로 측정되었습니다(Core: 6.41–6.65 µs). 이 픽스처는 채널이 하나이고 한도도 다르므로, 밀리초 규모를 교차 확인하는 용도일 뿐 주 매트릭스와 조건이 같은 대체 측정이 아닙니다.

## 다음 측정과 최적화 순서

1. Program의 시작/종료와 게시 직렬화를 프로파일링합니다. 인메모리 저장소와 C++ 제어에서도 작은 payload의 비용이 상당하므로, JS 엔진만 바꿔서는 전체 범위를 다룰 수 없습니다.
2. 측정한 SQLite/libpq 호출 횟수를 바탕으로, 같은 저널, 소유자, 권한, 예산, 원자성 보장을 유지하면서 줄일 수 있는 중복 읽기와 왕복을 조사합니다. 영속 커밋을 꺼서 더 좋은 수치를 얻어서는 안 됩니다.
3. payload 크기별 측정 결과로 정규 JSON 변환과 복사가 반복되는 지점을 조사합니다. 컴파일된 소스의 재사용은 워밍업된 제너레이터 실행과 따로 벤치마크합니다.
4. JIT 백엔드는 실제 JS CPU 작업을 분리한 뒤에 비교합니다. 이때 콜드 스타트 비용과, 현실적인 에이전트 수에서의 메모리도 포함합니다.

CPU 사용의 완전한 귀속, 동시 멀티 테넌트 처리량/공정성, 재귀 spawn, 실행 중 교체, 실제 JIT 비교는 아직 측정하지 않았습니다. 이 기준선을 위해 프로덕션 런타임을 최적화한 것은 없습니다.
