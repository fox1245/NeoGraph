# AgentXによる解析を伴う正規化JSONの最適化 — 2026-09-07

**Languages:** [English](PROGRAM_CANONICAL_JSON_OPTIMIZATION.md) | [한국어](PROGRAM_CANONICAL_JSON_OPTIMIZATION.ko.md) | [日本語](PROGRAM_CANONICAL_JSON_OPTIMIZATION.ja.md) | [简体中文](PROGRAM_CANONICAL_JSON_OPTIMIZATION.zh-CN.md)

測定した64 KiBのProgramのワークロードでは、文字列のスキャンとコピーをまとめて処理することで、すでに最適化済みのコマンドヘッドの実装（`ef56ff89`）と比べて、レイテンシーが、**メモリストアで約54%、SQLiteで約50%、PostgreSQLで約26%**減りました。この改善は、ネイティブの正規化JSONの処理によるものです。この実験では、JITバックエンドの評価は行っていません。

## この変更を選んだ根拠

オーナー側ローカルのAgentXのradare2 MCPピア（コネクターのバージョン1.8.6）が、固定したReleaseのELFを、内容のIDで指定して調べました。使ったのは、アーティファクトを開く操作、シンボルの検索、読み取り専用の逆アセンブルだけです。関数単位の逆アセンブルは、最初は、解析のメタデータがないと報告しました。読み取り専用のサービスは、`analyze` を公開していません。アドレスを指定した `disassemble` は成功し、結果は、`nm` で得たELFのシンボルのアドレスとサイズの範囲に限定しました。

次に、LinuxのソフトウェアCPUクロックのサンプラーを、新しく作成したベンチマークのプロセスとそのスレッドだけを対象にして、カーネルとハイパーバイザーのサンプルを除いて実行しました。周期は1 msで、CPUごとの継承されるバッファを使いました。これは、セットアップ、呼び出し側の検証、後始末を含む、プロセス全体のleaf-IPのプロファイルです。実時間の内訳でも、呼び出しを含めたコールグラフでもありません。解決できない共有ライブラリのシンボルは、解決できないものとして、そのまま残してあります。

- 小さなメモリの入力：サンプル4,196個、欠落なし。
- 64 KiBのメモリの入力：サンプル5,155個、欠落なし。`append_escaped` がサンプルの25.68%、UTF-8シーケンスの検証が17.58%、エスケープ後のサイズの計算が11.68%を占め、合わせて約55%でした。
- AgentXの逆アセンブルでは、古いループが `0x66a349` でUTF-8の検証を呼び出し、返されたシーケンス長だけ進んでいました。ASCIIのバイトでは、その長さは常に1でした。ソースの確認でも、エスケープ後のサイズを数えるループと、出力するループが、バイト単位で別々にあることを確認しました。

この根拠から、推測に基づくVMの変更よりも先に、文字列の処理を選びました。測定された改善は、以下の、プロファイラーを使わない別の比較で決まります。サンプリングAPIのリファレンス：[Linux perf_event_open](https://man7.org/linux/man-pages/man2/perf_event_open.2.html)

## 変更内容と不変条件

`src/core/canonical_json.cpp` は、8バイトの完全なワード単位で、ASCIIかJSONのエスケープ対象のバイトかを確認し、残りをスカラーで処理するようになりました。アラインされていないワードは、`memcpy` で読み込みます。繰り返しのバイトのマスクは、エンディアンに依存しません。UTF-8の検証は、ASCIIが続く区間を一度に消費し、ASCII以外の既存の有効性の規則は、そのまま保ちます。文字列の出力は、検証の後で、エスケープ不要な区間を、1回の操作で追記します。

サイズの計算は、生のサイズを下限として始め、そこにエスケープによる増加分を加えます。改行のような短いエスケープも含め、制御バイトごとに6バイトを見込む、もとの保守的な見積もりは保たれます。16 MiBの上限、不正なUTF-8の拒否、エスケープされるバイト、ソートされたキー、数値のエンコード、所有される値の動作、内容のIDは、変わりません。新しい依存、アーキテクチャ固有のコンパイラーオプション、公開API、SQLクエリ、永続化の設定は、導入していません。

変更後のELFも、同じAgentXのピアで調べました。`0x668710` にある `unescaped_prefix` は、`mov rax, qword [r8 + rcx]` を含み、`rcx` を8ずつ進めています。これは、意図したワイドロードのループが、コンパイル後のコードにあることを裏付けます。

## 正しさの検証

- 新しい正規化JSONのテスト6件は、ワード境界の前後にあるすべてのASCIIバイト、Unicodeとエスケープが混在する入力、決定的な4,096ケースのUnicodeコーパス、ASCIIの接頭辞の後の不正なUTF-8、短い、またはアラインされていないビュー、実体化後のサイズの保守的な境界を、対象にしています。
- 同じ6件のテストは、リーク検出を含むAddressSanitizerとUndefinedBehaviorSanitizerでも、suppressionなしで通りました。
- Coreに絞った211テストが、2回の実行で通りました。最初に180件、その後、専用のバックエンドを有効にして、PostgreSQLのチェックポイントのケース31件すべてです。
- Programスイート全体：680テストが通過。対象外のメモリストアのプロセス再起動のケース2件はスキップ。ゴールデンな正規のIDと、SQLiteおよびPostgreSQLでの復旧、系統、置き換え、予算のチェックを含みます。
- マイクロベンチマークの出力は、すべて、独立したスカラーのエスケープのオラクルと一致しました。Programの呼び出しは、すべて、期待されるカウンターとペイロード全体を保っていました。
- 検証は、WSL上のGCC 13.3で行いました。Windows、ARM、サニタイザーでのエンジン全体の適格性確認は、主張していません。

## 残っている課題

その後に取った、64 KiBのCPUプロファイルでは、サンプルを2,317個取得し、欠落はありませんでした。SHA-256によるIDの計算がサンプルの約35.17%、エスケープ不要な区間のスキャンが10.96%、UTF-8の検証が1.90%を占めました。ハッシュの割合が大きくなったのは、全体の仕事量が減ったためです。ハッシュが遅くなったことの証拠ではありません。解決できないコストをすべてメモリ確保やコピーのせいにする前に、共有ライブラリのシンボルについて、さらに正確な帰属が必要です。

## 再現方法と範囲

`ef56ff89` と、変更後のリビジョンで、同じReleaseのオプションを使って、`bench_canonical_json` と `bench_program_cost` をビルドします。新しいマイクロベンチマークのソースは、変更前のライブラリに対して、そのライブラリを変更せずにビルドできます。マイクロベンチマークのコマンドの例を示します。

```sh
bench_canonical_json unicode 65536 500
```

エンドツーエンドのケースには、[ペアで実行するProgramの比較](PROGRAM_COMMAND_HEAD_OPTIMIZATION.md)を使います。生のRPCのリクエストとレスポンス、ツールのスキーマ、ELFとソースのハッシュ、CPUのサンプルとマップ、ヘルパーのソース、マイクロベンチマークとランタイムの結果、テストのログは、ローカルの `artifacts/program-canonical-agentx-20260907/` に保存してあります。読み取り専用の入力ELFの完全なコピーは、割り当てられたAgentXのアーティファクトルートの、ダイジェストから決まるディレクトリに残してあります。エビデンスに、認証情報は含まれていません。

これは、オーナーが許可したホストから、AgentXの分析用ピアを直接使ったものです。AgentXのモデルのWorkOrderの起動、新しいToolBindingSetの公開、AgentXのAnalysis Graphへのレコードのインポートは、行っていません。それらのワークフローや来歴の保証は、主張していません。AgentXのサービス設定と、その他のアプリケーションのデータは、変更していません。
