# 子の合成の復旧の適格性確認

**Languages:** [English](PROGRAM_CHILD_SYNTHESIS_RECOVERY.md) | [한국어](PROGRAM_CHILD_SYNTHESIS_RECOVERY.ko.md) | [日本語](PROGRAM_CHILD_SYNTHESIS_RECOVERY.ja.md) | [简体中文](PROGRAM_CHILD_SYNTHESIS_RECOVERY.zh-CN.md)

N3は、レビュー済みのソース、1つの子、チェックポイントというシナリオを、SQLiteとPostgreSQLで適格性確認します。復旧は、記録済みの子の操作と、分類されていない外部への効果を、区別するようになりました。Coreのディスパッチに、永続的なチェックポイントも結果もない場合は、引き続き、明示的な照合を残します。

## 復旧の規則

復旧がディスパッチを検討する前に、親のコマンドジャーナルは、admission済みのProgram、コマンドの序数、ペイロード、効果のIDと一致していなければなりません。この復旧の経路をたどれるのは、`spawn`、または合成された `spawn` で終わる `await` の連鎖だけです。ホストは、グラント、元の世代、実際のコンパイルの引き落とし、生成されたバインディングを、あらためて検証します。以前に記録されたディスパッチも、子の実行IDと正規の入力が、正確に一致していなければなりません。

復旧は、そのコマンドの既存のリソースの予約と、オペレーションの引き落としを再利用します。同じコマンドに再び課金することも、別の動的コンパイルを許可することもありません。子の予約の再構築には、保留中のコマンドが保持しているリソースが含まれます。この再構築が変えるのは、プロセス内の会計上の見え方であり、永続的な予算ではありません。既存の子のレコードと最終結果が、引き続き正式なものです。

すでに存在する、同じ内容の `Compiling` や `Validating` の公開は、新しい呼び出し側がその処理を所有していることの証拠にはなりません。claimしたステージを開始できるのは、`Published` を受け取った書き込み側だけです。並行するコールドリカバリのテストでは、この公開の前に独立した2つのプロセスを同期させ、成功するワーカーが1つ、衝突が1つ、意味検証が1回であることを要求します。

## プロセス終了のマトリクス

各ケースでは、選んだ公開の直後に、デストラクターを実行せずにプロセスを終了し、その後、新しいCatalog、遷移ストア、チェックポイントストアを開きます。2つのデータベースで、同じケースを実行します。

| 中断した箇所 | 必要な復旧 |
|---|---|
| `Reserved` | 既存の予約から、1回だけコンパイルします |
| `Compiling` | 引き落としを保ち、照合を要求します |
| `Compiled` | バンドルを再利用します |
| `Validating` | 引き落としを保ち、照合を要求します |
| `Validated` | 意味検証のエビデンスを再利用します |
| `Admitting` | 固定されたadmissionを再利用します |
| `Admitted` | admission済みのバージョンをバインドします |
| `Bound` | 記録済みの親のコマンドを実行します |
| `Dispatching` | その子のIDと入力を再利用します |
| `Spawned` | 既存の子を復旧するか、不確かなCoreのディスパッチを明示的に照合します |
| 子の関係 `Publishing` | 既存の子の最初の公開を完了します |
| 子の関係 `Dispatched` | リプレイしても安全でないCoreの処理に、チェックポイントも結果もなければ、照合します |
| 子の最終結果 | 結果を再利用します。完了した子を再実行しません |
| 親への子の結果の接続 | 既存のjoinの結果を再利用します |
| 親のコマンドの結果 | 記録済みのコマンドの結果をリプレイします |
| 親の最終結果 | 同じ最終結果のIDを返します |

データベースごとに、プロセス終了の境界が16個あり、さらに、2プロセスでの復旧の競合が1つあります。テストでは、元の子のID、永続的な子の関係が1つであること、コンパイルの引き落としが1回であること、保持されたコマンドのオペレーション数も確認します。実行マーカーによって、完了した子の処理が、プロセス終了をまたいで繰り返されないことを確認します。

## 子の実行が不確かな場合

`Dispatched` の関係だけでは、プロセスが消える前に、Coreの処理が実行されたかどうかは分かりません。子が実行中として記録されたままで、正確なチェックポイントがなく、そのプランがチェックポイントなしではリプレイしても安全でない場合、親の再接続はフェイルクローズになります。`recover_child_synthesis` は、子のIDと入力を保持したまま、`P_CHILD_SYNTHESIS_CHILD_UNCERTAIN` とともに `ReconciliationRequired` を記録します。

アクティブでない親に対するこの復旧のチェックが、生きている親への再接続を、失われた実行として誤って分類することはありません。生きている親への再接続では、既存の試行が返ります。

不確かさの扱いは、合成のレコードがすでに `Spawned` になっている場合にも適用されます。レコードは、過去のアーティファクトを変えずに、その照合の扱いを追記できます。代わりの子を作ることも、成功した結果を捏造することもありません。自動で照合を承認するAPIは、この変更では提供されません。

## 追加のチェック

- 予約の応答が失われ、その後で合成の履歴が読めなくなっても、コンパイルの1単位が返却されることはありません。読み取りが回復すると、元のリクエストが再利用されます。
- PostgreSQLのテストでは、予約のトランザクションの内側から、データベースの接続を切断します。新しい接続からは、元の親が見え、途中までの予約はありません。その後の試行は、1回だけ引き落とします。
- 意味検証の最中にキャンセルしても、admissionにも子のディスパッチにも到達しません。
- Catalogのアクティベーションで、生成されたバインディングを別のバージョンに向け直すことはできません。
- 保持のピンが、必要なバージョンを保護します。ホストが子のバージョンを削除した場合、キャッシュされた合成のエビデンスでは、それを実行できません。すべての合成の履歴から保持のルートを自動で集める処理は、引き続き、ホストの責任です。
- Programの置き換えでは、コンパイルの引き落としが保持されます。古い実行の、結び付けられていない生成済みのバインディングは、後継の世代に移されません。結び付けられている子孫は、[再帰的なHarnessの契約](PROGRAM_RECURSIVE_HARNESSES.md)によって、保持できるようになりました。
- PostgreSQLのテストは、プロセス終了のマトリクスと接続切断のケースを含め、既存のCTestのデータベースリソースのロックを共有します。

## この適格性確認の限界

これは、記載した縦のシナリオに対する、プロセスと接続の障害に関する適格性確認です。外部への効果が常にちょうど1回であること、電源断、ホストをまたぐデータベースのフェイルオーバー、不確かなCoreやプロバイダーの結果の自動解決については、主張しません。ホストの異なる効果が混在する、一般的な構造化されたjoinは、従来の照合の動作のままです。複数の生成された子のツリー、任意の外部バリデーターの最中のキャンセル、グラフのマイグレーションの完全な組み合わせ、保持のルートの自動検出、合成の性能やストレージの増加に関する適格性確認には、別の検証が必要です。

ホストの統合については[永続化の契約](PROGRAM_CHILD_SYNTHESIS_PERSISTENCE.md)を、変わっていない、レビュー済みのソースと権限の境界については[認可の契約](PROGRAM_CHILD_SYNTHESIS_CONTRACT.md)を参照してください。
