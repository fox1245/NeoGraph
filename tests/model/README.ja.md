# joinのモデル（#363）

**Languages:** [English](README.md) | [한국어](README.ko.md) | [日本語](README.ja.md) | [简体中文](README.zh-CN.md)

`BarrierJoin.tla` は、BSPのスーパーステップを、ANDのjoinを1つ持つ形でモデル化したものです。このjoinの `wait_for` のスロットには、複数の `any_of` の選択肢を入れられます。これが#363で承認された範囲で、joinのモード（join modes）は先送りしています。`tests/test_join_exhaustive.cpp` は、同じルールをリファレンスインタープリターとして記述し、実際の `Scheduler` と `GraphEngine` を、より大きなグラフでそのインタープリターと照合します。セマンティクスを変えるときは、この2つを揃えて更新してください。

## ルール

- スロットは、その選択肢のどれか1つがjoinにシグナルを送ると埋まります。joinは、すべてのスロットが埋まった時点で発火し、そのあと、蓄積されたシグナルはすべてクリアされます。
- メンバーでないノードからのシグナルは記録されますが、数えられません。
- 条件付きルートは、ラベルを非決定的に選びます。
- `Command.goto(__end__)` は、そのスーパーステップのすべてのルートに優先します。
- 実行可能なノードがなくなると、実行は終了します。joinにシグナルが残っている場合（メンバーからのものかどうかは問いません）、実行はストールして `Failed` になります。ただし、最後のスーパーステップ（その後に実行可能なノードがなくなるステップ）が、明示的なルートで `__end__` に到達した場合は除きます。明示的なルートとは、`__end__` への静的なエッジ（`.exit()` が書くもの）、`__end__` への条件付きルート、`Command.goto(__end__)` のいずれかです。暗黙の終了（後続のないノード）では、ストールは抑止されません。それより前のスーパーステップでの明示的な終了も、抑止しません。

つまり、joinが抜けるスーパーステップで届いた、`any_of` の余った選択肢があっても、実行は完了します。1スーパーステップ後に届き、ほかに実行可能なノードがない場合は、失敗します。

C++のハーネスは、失敗ルート（#364）も対象にしています。失敗したノードは、その失敗エッジのターゲットだけにルーティングされ、`Command.goto` は引き続きそれに優先します。失敗のターゲットがjoinや `__end__` になることはないので、上のルールはそのまま成り立ちます。このTLA+モデルには、失敗エッジは含まれていません。

## 不変条件

| 名前 | 意味 |
|---|---|
| `NoDoubleFirePerRound`、`JoinRunsOnlyWhenFired`、`FireClearsSignals` | 発火のたびに、前回の発火以降に届いたシグナルのうち、すべてのスロットを埋めるものが消費される。joinが実行されるのは、発火の直後だけで、発火するとすべてのシグナルがクリアされる。 |
| `StallImpliesFailed`、`FailedOnlyOnStall` | joinにシグナルが残ったまま終了する実行は失敗し、失敗するのはそのような実行だけである。 |
| `OnlyExplicitEndSuppressesStall` | シグナルが残ったまま完了する実行は、最後のスーパーステップで、明示的に `__end__` に到達している。 |
| `LeftoverAlternativeStalls` | joinが発火した後に届いた選択肢が、あとの発火もなく、最後のスーパーステップに明示的な終了もない場合は、実行が失敗する（フェイルクローズ）。 |
| `NamedOutcomes` | #357の、排他的でない2つのバリエーション：余った選択肢が終了と同時に届けば完了し、1スーパーステップ後に届けば失敗する。 |
| `LegacyEquivalence` | スロットが単一要素のときは、スロットのルールは現在のバリアと同じになる。`wait_for` が、受信したシグナルの部分集合になる。 |
| `Termination`（プロパティ） | すべての実行は、完了するか、失敗するか、ステップの上限に達する。 |

## TLCの実行

TLCはCIには含まれていません。Java 11以降と、TLA+のリリース（<https://github.com/tlaplus/tlaplus/releases>）にある `tla2tools.jar` が必要です。

```sh
cd tests/model
java -XX:+UseParallelGC -cp /path/to/tla2tools.jar tlc2.TLC \
    -workers auto -config BarrierJoin.cfg BarrierJoin.tla
```

`BarrierJoin.cfg` は、ノードが3つ以下のすべてのグラフについて、joinのメンバーの `any_of` の分割をすべて試して検査します。さらに、仕様に挙げた#357のグラフ（従来のバリア、`any_of` のスロット、排他的でない2つのバリエーション、`Command.goto` による明示的な終了）も検査します。TLCは、異なる状態を335,521個見つけ、エラーは見つかりませんでした。8ワーカーで2分かかる処理の大半は、21,707個の初期状態の計算に使われます。`MaxNodes = 4` は、TLCでは扱えません。C++のハーネスは、5ノードまでを対象にしています。

不変条件が実際に働くことを確かめるには、暗黙の終了でストールを抑止するようにするか（`StallImpliesFailed` が失敗します）、メンバーのシグナルが1つ届いただけでjoinを発火させます（`NoDoubleFirePerRound` が失敗します）。

## 再開のモデル

`tests/resume_model.h` と `tests/test_resume_model.cpp` は、joinのハーネスがjoinを検査するのと同じように、`GraphEngine` の割り込み、再開、リプレイの契約を、リファレンスインタープリターと照合します。`tests/test_program_resume_model.cpp` は、Programのランタイムについて、同じ検査を行います。リファレンスが表しているのは、ドキュメント（`docs/concepts.md`）に書かれた契約です。スーパーステップは、実行可能なノードを実行し、続いてそのSendを実行します。呼び出しが質問を出したステップは、そのすべてで一時停止し、完了したものは保持します。再開は、指名された割り込み、指名がなければ最初の割り込みに答え、その呼び出しだけが値を受け取ります（#388、#393）。`interrupt_before` の承認は、保留されていたノードに届きます。ステップの各ゲートには個別に答え、答えたゲートだけが通過します（#382、#396）。失敗は、同じステップの通常の割り込みに優先します（#392）。

### Coreのハーネス

- **ファミリー。** メインのノード `n0`..`n{N-1}` を、前方へのエッジ（各ノードの後続は最大2つ）でつなぎ、すべてのノードに到達できるようにします。各ノードの種類は、次のとおりです。`Ok`、`Ask`（答えが来るまで `NodeInterrupt` を投げる。後続が2つある場合は、答えに応じてルーティングすることがある）、`Fail`（失敗エッジの有無は問わない、#364）、`Flaky`（失敗し、その後のリトライが独自の試行の名前空間で成功する）、`Map`（`Ok`、`Ask`、`Fail` のいずれかの項目を持つワーカーに、1つまたは2つのSendを送る）。静的な先行ノードが2つある最後のノードを、オプションでバリアのjoinにします。また、`Ok` か `Ask` のノードを1つ選び、`interrupt_before` か `interrupt_after` を付けます（拡張した範囲では、`interrupt_before` のゲートを2つ付けます）。
- **スケジュール。** リファレンスの回答の順序をすべて試します。保留中の各質問に、割り込みIDを指定して答える場合と、デフォルトで答える場合があり、答えに応じてルーティングする `Ask` では、両方のラベルを試します。各スケジュールは、永続化される操作ごとにクラッシュさせる場合（各チェックポイントの `save` と `put_writes`。それぞれの前と、最後の後。拡張した範囲では、それぞれの前と後で、さらに復旧中にもう一度クラッシュさせる）と、すべての一時停止をフォークする場合でも実行します。クラッシュするとプロセスが止まり、ストアはそれ以降の操作をすべて拒否します。ホストは、実際のホストと同じように、最新のチェックポイントから復旧します。そのチェックポイントが、実行中の再開で答えたものであれば、その再開をやり直します。見ていない `interrupt_before` か `interrupt_after` の一時停止があれば、それを表に出します。そのほかの場合は、値なしで再開します。チェックポイントのないスレッドは、最初から実行し直します。すべてのスケジュールを `InMemoryCheckpointStore` で実行します。`SqliteCheckpointStore` では、粗い時計を使って、クラッシュなしで実行します（ノードが2つ以下のグラフ、拡張した範囲では3つ以下のグラフでは、クラッシュも含めます）。粗い時計では、すべてのチェックポイントが同じタイムスタンプで保存されます（`tests/fixtures/coarse_clock_store.h`）。
- **質問。** すべてのスケジュールを2通りで実行します。1つは、自分の呼び出しIDに宛てた回答だけを受け取る質問、もう1つは、承認ノードのように、どの再開の値でも受け取る質問です。
- **プロパティ。** P1（ちょうど1回）：ノード本体の完了が永続化された後（そのpending write、またはそのステップのコミットの後）に、その本体が完了し直すことはありません。本体が再び動くのは、クラッシュで完了の記録が失われた場合だけです。P2（質問がすべて出る）：一時停止と、保留中の質問およびそのペイロードが、リファレンスと一致し、各 `Ask` は与えられた回答だけを消費します。P3（結果が同じ）：ステータス、ログ、失敗のレコード、ルートが、リファレンスと一致します。P4（クラッシュの透過性）とP5（フォークの同値性）：P1〜P3が、すべてのクラッシュとフォークのスケジュールで成り立ちます。

### Programのハーネス

対象は、JavaScriptの `main()` のプログラムと、型付きのプランです。JavaScriptのプログラムは、`callCore`、`ng.all`、`ng.race`、2つのメンバーを持つ `ng.quorum`（同時に実行する場合と1つずつ実行する場合）、`ng.await`、2つのノードを実行するCoreのステップを呼び出す `callCore`（両方が質問することがある、#388と#394）です。型付きのプランは、`parallel`、3つのうち2つの `quorum`、`sequence` で、いずれも、バインド済みのプロバイダーを呼んだり、質問したりするノードを1つ持つCoreの上で動かします。ホストは、`LocalProgramHost` が組み立てるのと同じ構成にします。インメモリの場合は、インプロセスの課金付きブローカーを使います。SQLiteの場合は、すべてのストアを1つのSQLiteファイルに置き、チェックポイントを同じ粗い時計で保存し、SQLiteのプロバイダージャーナルを使います。プロバイダーは、本物のSDKのクライアントで、送信したリクエストを数えるローカルのトランスポートの上で動きます。P1には、「1回だけ送信し、1回だけ課金する」も含まれます。実行に課金されるリクエスト、トークン、金額が、リファレンスと一致します（インプロセスのブローカーでは、ドキュメントに書かれているとおり、再実行されたノードは、再び呼び出して再び支払います）。クラッシュのテストは、呼び出しを1つずつ実行するプログラムについて、SQLiteのホストで行います。チェックポイントの保存、`put_writes`、Programの遷移、プロバイダーのディスパッチ、ジャーナルに記録された呼び出しのたびに、データベースをコピーし、そのコピーの上で新しいランタイムが実行に再接続します。

ハーネスは、P4とP5の対象外であるものの、ドキュメントに書かれた挙動に沿ったスケジュールと、それらが契約に投げかける疑問を、失敗とはせずに報告します。JavaScriptのコマンドの中でクラッシュすると、実行は照合のために返されます。最初のCoreチェックポイントの前に止まったプランは、復旧されません（`P_RUN_RECOVERY_BLOCKED`）。リクエストが出ている最中にクラッシュすると、その呼び出しはホールドされ、二度と送信されません。一時停止した実行をフォークすると、一時停止した呼び出しが質問を出す前に行ったプロバイダー呼び出しを、再び送信し、再び課金します。元の実行を再開した場合は、その呼び出しがリプレイされます。

### 範囲と変数

| | CIの範囲 | `NEOGRAPH_RESUME_MODEL_BOUND=extended` |
|---|---|---|
| メインのノード、特殊なノード | 3、2 | 4（特殊なノードは、ノードが3つまでなら3、4つなら2） |
| 回答、スケジュールごとのクラッシュ | 4、1 | 6、2 |
| Sendの項目 | `ok`、`ask`、`ask ok`、`ask ask`、`ask fail` | 1つまたは2つのすべてのパターン |
| ゲート | 1つ、`Ok` か `Ask` に付ける | 任意のノードに1つ、または`interrupt_before`を2つ |

CIの範囲では、Coreのハーネスは2,196個のグラフを実行し、質問の種類ごとに約6,100通りの回答のスケジュール、それぞれ約83,000回の実行を行います。Programのハーネスは、124個のJavaScriptプログラムと18個のプラン、約950通りのスケジュールを実行します。どのテストも、4ワーカーで1分以内に終わります。

変数：`NEOGRAPH_RESUME_MODEL_NODES`、`_SPECIAL`、`_SPECIAL_LARGEST`、`_ANSWERS`、`_CRASHES` は、個別の上限を上書きします。`NEOGRAPH_RESUME_MODEL_SQLITE=0` は、SQLiteを対象から外します。`NEOGRAPH_RESUME_MODEL_THREADS` は、ワーカー数を指定します（デフォルトは4）。Programのハーネスでは、`NEOGRAPH_PROGRAM_RESUME_MODEL_BOUND=extended` を指定すると、2コマンドのプログラム、すべてのフォーク、すべての操作の後のクラッシュが追加されます。`_ONLY` は、説明にその文字列を含むプログラムだけを残します。`_CRASHES=0` は、クラッシュを対象から外します。`_THREADS` は、ワーカー数を指定します（デフォルトは4）。`_DEBUG` は、すべての結果と永続化される操作を出力します。
